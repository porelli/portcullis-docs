Upgrading & Releases¶

Upgrade an installation from the core checkout with:

git pull
./portcullis upgrade

upgrade is safe to re-run. Every step it performs is idempotent, and it backs up first.

What portcullis upgrade does¶

  1. Fills in missing secrets. It generates HUB_PROXY_SECRET, FORWARD_AUTH_CLIENT_SECRET, FORWARD_AUTH_COOKIE_SECRET, LLDAP_JWT_SECRET or BACKUP_PASSWORD if they are empty or missing. Nothing on disk depends on those. The database and admin passwords must already be in .env, and the command stops if one is missing.
  2. Checks the networks. It validates the portcullis-proxy and portcullis-auth settings in .env against the existing Docker networks, and stops with instructions if they differ.
  3. Backs up with portcullis backup, a consistent online backup: Vault raft snapshot, pg_dump, the LLDAP/Hub/ACME volumes, .env, certs/ and secrets/. It goes to backups/<timestamp>/. Skip this with --skip-backup.
  4. Pulls images. Core images are pinned by digest in docker-compose.yml, so the pull only changes something when the pins changed in the commit you pulled. The Hub image comes from HUB_IMAGE (see below).
  5. Re-runs the setup steps.
    • vault init: unseal, enroll AppRole and policy.
    • pki setup: rewrites the client-cert role, so a changed CLIENT_CERT_TTL applies to new certificates, and refreshes the Keycloak truststore and CRL settings. An existing CA is never replaced.
    • Rebuilds certs/ca-bundle.crt.
  6. Restarts the stack with docker compose up -d --build and waits for Vault, PostgreSQL, LLDAP and Keycloak to be healthy. Traefik, forward-auth and Keycloak are restarted if the CA chain or truststore changed.
  7. Re-applies the identity config. It runs keycloak configure (realm settings, X.509/CRL settings, scopes, LDAP bind) and oidc register (client secrets from .env), then recreates forward-auth so it picks up a newly generated client secret.

Check the result with ./portcullis status.

Apps enabled in the Hub are separate compose projects. upgrade does not restart them. The Hub reconciles them on start and reports anything that is not running as drift.

Backups and rollback¶

The backup made by upgrade is a normal local backup (see Backups). It contains the Vault unseal key and root token, so it can decrypt the CA. Protect it like the keys themselves. upgrade does not upload it off-host: run ./portcullis backup --offsite first if you want an off-host copy of the pre-upgrade state.

To roll back, check out the previous core commit (or release) and restore the backup:

./portcullis restore --list
./portcullis restore backups/<timestamp>

restore saves the current .env, secrets/ and certs/ to backups/pre-restore-<timestamp>/ before overwriting them.

Versions and releases¶

How the four repositories are versioned is defined in Integration Contracts §1:

  • Tags. Every repo uses semver tags vMAJOR.MINOR.PATCH. A breaking change to an integration contract bumps MAJOR in every repo it affects.
  • Core images are pinned tag@sha256:digest in every compose file and profile, so a core commit fully determines which Traefik, Keycloak, Vault, LLDAP, oauth2-proxy, PostgreSQL, socket-proxy and monitoring versions run. Dependabot proposes updates weekly; CI fails on anything unpinned.
  • Templates. The Hub tracks the default branch of each template source; pull updates with Sync in the Hub. The templates CI tests against the core ref in its .core-ref.

Check what you run:

./portcullis version          # core version (VERSION file or git describe) + Hub image
./portcullis version --json

Core releases¶

A core release is a vX.Y.Z tag. .github/workflows/release.yml publishes it only if all of the following holds:

  1. Tag and changelog. The tag is vMAJOR.MINOR.PATCH, and CHANGELOG.md (Keep a Changelog) has a ## [X.Y.Z] section.
  2. Pinned Hub. The HUB_IMAGE default in docker-compose.yml is a released Hub tag pinned by digest (ghcr.io/porelli/portcullis-hub:A.B.C@sha256:…). That tag must be a published, non-prerelease Hub release that still resolves to that digest.
  3. CI. The full core CI (ci.yml, called as a reusable workflow) passes on the tagged commit.

Then it publishes:

  • release notes: the changelog section, the pinned Hub image, and GitHub's generated notes
  • portcullis-X.Y.Z.tar.gz: the checkout without .git, plus a VERSION file. The tarball is reproducible: sorted, numeric owner, commit time
  • portcullis-X.Y.Z.tar.gz.sha256

Install or upgrade from a release tarball:

sha256sum -c portcullis-X.Y.Z.tar.gz.sha256
tar -xzf portcullis-X.Y.Z.tar.gz && cd portcullis-X.Y.Z

Or check out the tag in your git checkout: git fetch --tags && git checkout vX.Y.Z.

Hub image¶

HUB_IMAGE selects the Hub:

  • On core main the default is ghcr.io/porelli/portcullis-hub:edge, the latest build of the Hub's main.
  • A core release pins a released Hub tag by digest, as described above.

  • Overriding it in .env? Use a released tag and its digest, never edge in production:

    HUB_IMAGE=ghcr.io/porelli/portcullis-hub:1.2.3@sha256:<digest>

Hub releases are published as X.Y.Z, X.Y, X and sha-<short>. There is no latest tag. Each image is signed with cosign (keyless, GitHub OIDC). Verify it before you pin it:

cosign verify ghcr.io/porelli/portcullis-hub:1.2.3 \
  --certificate-identity-regexp '^https://github.com/porelli/portcullis-hub/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
docker buildx imagetools inspect ghcr.io/porelli/portcullis-hub:1.2.3   # top-level Digest:

No releases yet

No repository has been tagged yet. Core main therefore runs the Hub's edge, and the templates CI tests against core main. CHANGELOG.md collects everything under [Unreleased].

Changing settings during an upgrade¶

You changed Run
ACME_STAGING or MTLS_ENABLED ./portcullis config apply && ./portcullis up
CLIENT_CERT_TTL ./portcullis upgrade (or ./portcullis pki setup); only new certificates are affected
FORWARD_AUTH_CLIENT_SECRET ./portcullis oidc register && ./portcullis up
An empty rotatable secret (to rotate it) ./portcullis upgrade generates a new one
HUB_IMAGE ./portcullis up
Network ranges See Security & Hardening → Networks. Docker can't change an existing network in place
