Security & Hardening¶

This page covers what the core stack (docker-compose.yml in the core repo) does to limit the damage a compromised component can do, and where it can't: the threat model, network layout, Docker socket proxies, per-service container settings, the secrets containers read, and header trust.

Threat model summary¶

Asset / boundary Threat Mitigation
Logins Phishing, password reuse WebAuthn (FIDO2) and PIV client certificates. Both are bound to the origin or the TLS handshake. Per-app policies can require them
User identity A user changes their own LLDAP email to someone else's Identity is the immutable username everywhere; email is never used to authorise or link accounts
Identity headers (X-Forwarded-User, client-cert headers) Spoofed by an internet client Traefik deletes client-supplied X-Forwarded-* and cert headers on the entrypoint, and forward-auth replaces the identity headers
Attribute headers (X-Forwarded-Attr-*) Spoofed by an internet client or by routers without forwardAuth Client copies stripped by authResponseHeadersRegex: ^X-Forwarded-Attr- on every forwardAuth middleware (Traefik can't delete headers by prefix in a headers middleware). Routers without forwardAuth (keycloak, vault-ui, enroll-invite, headscale, netbird, docs) don't strip them; backends there must not trust them
Identity headers Spoofed by another container on portcullis-proxy Header-auth apps trust only Traefik's fixed IP (PORTCULLIS_TRAEFIK_IP). Keycloak trusts proxy headers only from Traefik's fixed IP on the internal portcullis-auth network
Hub (runs compose, so it is effectively host root) Reached without passing forward-auth Hub: requires lldap_admin and the X-Portcullis-Proxy-Secret header. People listener (people.<domain>): any signed-in user (group-gate-map.conf people=*), per-request permission checks
Docker API A compromised Traefik or Hub takes over the host No service mounts the socket except two socket proxies with per-client allow-lists
Lost or stolen YubiKey cert Keeps working until expiry Revocation is checked on every request (group-gate), at Keycloak X.509 login (CRL, fail closed), and by the mTLS binding. On removal or expiry, group-gate also withholds Authorization and X-Forwarded-Access-Token
Expired group membership Keeps working while Hub is down Every pending expiry is in the policy file's expiring array (plus a 10-min grace after LLDAP removal). group-gate treats it as absent. The Hub also revokes Keycloak sessions (oauth2-proxy cookie refresh is 1 min, so removals and Keycloak logouts take effect within ~1 min; sessions end at Keycloak's idle 8h / max 12h)
Path-based admin areas Bypassed with encoded or dot-segment paths group-gate normalises the path and denies ambiguous encodings (see Groups)
Templates (outside contributions) A malicious or careless template opens access The Hub rejects routing it can't fully see, refuses subdomain collisions and core subdomains, validates custom overrides (no Traefik labels, host-path bind roots, privileges), and fails closed on unknown config. Templates CI lints fork PRs without secrets
Public exceptions (share links, off unless an admin turns them on) Anonymous access to app endpoints, token guessing, share-password brute force, identity spoofing on header-auth apps Only declared, validated prefixes; listed mode routes only admin-listed share tokens; identity headers stripped; rate-limit@file; see Public exceptions
Vault data volume Copied off the host Encrypted. The unseal key is in secrets/ on the host, so a copy of the volume alone is useless
Host root / docker group Full compromise Out of scope. Anyone who can run docker is root-equivalent, and the unseal key is on the host

Known limits:

  • The Hub can still start arbitrary containers (privileged, host mounts): that is what "run compose for any template" means. Treat it as host root.
  • Auto-unseal trades confidentiality at rest for availability on the same host (see TLS & mTLS).
  • Routers without portcullis-groups@docker don't get revocation checks. They also get no group or path checks.

Public exceptions¶

An app's public exceptions are the one place where Portcullis deliberately lets unauthenticated internet traffic reach an app. What a turned-on exception exposes:

  • Every endpoint under each opened prefix, to anyone, without login, group, hardware key or policy. Only the app's own checks remain (share token, share password, expiry, download limits). In mode all that includes guessing share tokens; in mode listed only the listed shares are routed, and any other token on the same prefix still goes through forward-auth.
  • The app's share-password form (e.g. Nextcloud /s/<token>/authenticate) to brute force. Only the app's own brute-force protection and Traefik's rate-limit@file (50 req/s average, burst 100, per client IP) limit it. The app must see the real client IP (e.g. Nextcloud's TRUSTED_PROXIES = Traefik) or its limiter locks out everyone at once.
  • Static files under supporting paths (assets, l10n, theming; matched by extension, e.g. Grafana /public/plugins reveals installed plugins), and the few exact routes a template justifies. A front controller that routes extension-suffixed paths to code (Nextcloud's /apps/theming/theme/<id>.css, /core/js/oc.js) still runs those #[PublicPage] routes.
  • Uploads where the app allows them on a share (Nextcloud file drop via /public.php/dav).
  • The host's TLS tier. With an mTLS-only policy the host drops from protected@file to authaware@file: group-gate still enforces the client certificate per request on gated routers, but native-OIDC apps then check it only at login (Keycloak acr), and routers without group-gate not at all.

What it can't do:

  • reach paths outside the prefixes: the router matches Path(p) / PathPrefix(p/) on Traefik's sanitised path (dot-segments resolved), so /s/x/../../apps/files is matched as /apps/files and stays gated;
  • overlap admin paths, login gates or other routers of the app (the Hub refuses the template), or /admin, /oauth2, /.well-known;
  • carry an identity: X-Forwarded-User, X-Forwarded-Email, the other forward-auth headers, Remote-* and the template's identity_headers (and their _ forms) are deleted, so a header-auth app (Grafana) can't be told who the visitor is;
  • carry a login past the hardware key: core's public guard (group-gate /public-guard, first middleware of every public router) answers 403 to requests with Authorization, Proxy-Authorization, the template's credential_headers, credential_cookies or credential_query. Cookie and query names are normalised the way PHP does (php-src php_register_variable_ex: leading spaces, /. → _, name[…], NUL), raw and percent-decoded, case-insensitively; non-UTF-8 names are refused. It also denies any path outside the published patterns, a #, and encoded /, \, NUL or #. A plain session cookie the template doesn't list (Nextcloud's oc<instanceid>, needed for share passwords and CSRF) is passed; it only reaches share-scoped routes and static files there;
  • be opened by a template on its own: the Hub generates the router, only while an admin (or a template default that opens nothing until an admin lists a share) has it on, and reports any running exposure label that differs from what it would render as drift.

Trade-off: an app user signed in with a remember-me cookie gets the guard's 403 on a public link in the same browser (open it in a private window). The guard serves only version 4 of the policy file, so the Hub and core are upgraded together.

Not everything with a share feature can be scoped: Vaultwarden Send needs the web vault at / and the password-login token endpoint, and Kanboard's router reads ?controller= before the path, so neither declares public exceptions.

CI checks that exactly keycloak and traefik are on portcullis-auth, and that each socket-proxy network has exactly its two members.

Changing the ranges. Only do this if the defaults collide with a host, LAN or VPN network, ideally before ./portcullis init. The rules:

  • the IP range must be inside its subnet
  • the range must not contain the Traefik IP
  • the two subnets must not overlap

./portcullis up and upgrade validate them and refuse to run when an existing network has different IPAM:

  • portcullis-proxy: disable the apps in the Hub, ./portcullis down, docker network rm portcullis-proxy, ./portcullis up, then re-enable the apps so their env picks up the new Traefik IP.
  • portcullis-auth (core only): ./portcullis down && ./portcullis up.

Docker socket proxies¶

No service mounts /var/run/docker.sock except two linuxserver/socket-proxy containers (HAProxy, pinned by digest). Each sits on its own internal network, shared with exactly one client (integration contract §6):

Proxy Client Network Allowed API sections (1) Methods
socket-proxy-traefik Traefik (TRAEFIK_PROVIDERS_DOCKER_ENDPOINT=tcp://socket-proxy-traefik:2375) socket-proxy-traefik CONTAINERS, NETWORKS, EVENTS, VERSION, PING GET/HEAD only (POST=0)
socket-proxy-hub Hub (DOCKER_HOST=tcp://socket-proxy-hub:2375) socket-proxy-hub CONTAINERS, IMAGES, NETWORKS, VOLUMES, EXEC, EVENTS, INFO, VERSION, PING, ALLOW_LOGS All. POST=1 also allows PUT/DELETE on the allowed sections

The Hub's set is what docker compose up/down/ps/logs and the Hub's own Engine API calls (status, logs, exec, events) need:

  • containers: create, start, stop, kill, rm, inspect, list, wait, logs, exec
  • images: pull (/images/create) and inspect
  • networks and volumes: create, inspect, rm
  • /events, /info, /version, /_ping

Everything else is denied: BUILD, COMMIT, SWARM, NODES, SERVICES, TASKS, SECRETS, CONFIGS, PLUGINS, SYSTEM (df / prune), AUTH, DISTRIBUTION, SESSION, and container archive / export. CI runs a real docker compose project through socket-proxy-hub and checks the denials.

Limits of a socket proxy. The Hub can still create containers with any HostConfig (privileged, host bind mounts): that is inherent to "runs compose for arbitrary templates". The proxy removes the rest of the API surface (swarm, plugins, image builds, system prune, secrets). Treat the Hub as host-root-equivalent and keep it behind lldap_admin and the proxy secret.

Container hardening¶

Every core service gets:

  • security_opt: [no-new-privileges:true] and cap_drop: [ALL]
  • mem_limit and pids_limit
  • an image pinned tag@sha256:digest. The Hub comes from HUB_IMAGE; enroll and group-gate are built from enroll/Dockerfile / group-gate/Dockerfile, whose base images are pinned. group-gate's Python dependencies are exact pins with hashes in group-gate/requirements.txt, installed wheels-only with pip install --require-hashes

CI fails if any of these is missing.

The Hub never sees the core .env. It gets secrets/hub/core.env, which holds only what templates may reference: PORTCULLIS_DOMAIN, PORTCULLIS_TRAEFIK_IP, the proxy subnet and range, PORTAL_DISPLAY_NAME, HEADSCALE_*, HEADPLANE_*, NETBIRD_*, COTURN_*, and the names listed in HUB_SHARED_ENV. Core secrets are refused. ./portcullis up rewrites the file in place. secrets/ and backups/ are masked from the Hub with empty tmpfs mounts.

Header spoofing protections¶

  • Entrypoint. The websecure entrypoint has no forwardedHeaders.trustedIPs, so Traefik deletes client-supplied X-Forwarded-* and X-Forwarded-Tls-Client-Cert(-Info) headers. aliasHeadersStrategy=delete also drops alias spellings such as X_Forwarded_Tls_Client_Cert. The cert headers that group-gate, enroll and Keycloak see therefore always describe a certificate Traefik verified.
  • Forward-auth headers. Traefik's forwardAuth deletes every authResponseHeaders entry from the upstream request and re-adds only the values oauth2-proxy and group-gate return. A client can't send its own X-Forwarded-User or X-Auth-Request-Groups through.
  • No stale groups from Keycloak's cache. Keycloak's LDAP federation runs with cachePolicy=NO_CACHE (realm export, enforced on existing realms by ./portcullis keycloak configure): a removed membership or changed attribute in LLDAP is in the user's next token (forward-auth refreshes every minute), not held in a cached user until eviction or the daily sync.

  • Identity is the LLDAP username, never the email. LLDAP lets users edit their own mail, including to someone else's address. So:

    • Keycloak's LDAP federation does not trust it (trustEmail=false, tokens carry email_verified=false).
    • oauth2-proxy's session user is always the token's sub (Keycloak's user UUID). Its alpha userIDClaim is only a deprecated alias of emailClaim, so it is not used (CI rejects it). Instead oauth2-proxy/alpha.yaml builds X-Auth-Request-User, X-Forwarded-User and X-Auth-Request-Preferred-Username from the preferred_username claim, keeps emailClaim: email, and accepts the unverified email (insecureAllowUnverifiedEmail) because nothing authorises by it.
    • group-gate reads the username only from X-Auth-Request-Preferred-Username (set by portcullis-auth, which must run first) and denies the request when it is missing. It never falls back to the email or sub.
    • Apps get X-Forwarded-User / X-Auth-Request-User = immutable username, and X-Forwarded-Email / X-Auth-Request-Email = email (display only).
    • Every identity header is in the forward-auth middlewares' authResponseHeaders, which is what strips client-supplied copies.
    • Apps also get X-Auth-Request-Groups. All of these headers are authResponseHeaders of the forward-auth middlewares, so Traefik deletes client-supplied copies (the e2e test sends spoofed ones). Header-auth apps must log users in by X-Forwarded-User as a username and take the email from X-Forwarded-Email.
    • enroll and the Hub use X-Forwarded-User as-is (no email → username lookup). group-gate's mTLS binding compares the cert CN with that same username and requires the token's preferred_username to match it.
    • Native-OIDC apps must key accounts on sub / preferred_username and must not link existing accounts by email (e.g. Vaultwarden SSO_SIGNUPS_MATCH_EMAIL). Apps that insist on email_verified=true need their "allow unverified email" option.
    • Apps that refuse email_verified=false but accept it absent (Vaultwarden SSO signups) get the email-unverified client scope instead of email (manifest email_verified_claim: false): the email claim without email_verified. The email is no more trusted than before. Vaultwarden still matches pending email invitations by email, so its template turns invitations off (INVITATIONS_ALLOWED=false, SIGNUPS_ALLOWED=false) and gates the SSO login paths with group-gate (users_vaultwarden).

    Rule: email is never an identity or account-linking key. - Header-auth apps accept identity headers only from ${PORTCULLIS_TRAEFIK_IP}, through the app's proxy allow-list or a small gate in front of it. Templates CI checks this statically and with a forged request (see Header Auth Pattern). - Keycloak accepts proxy headers only from PORTCULLIS_AUTH_TRAEFIK_IP on portcullis-auth, decided by the TCP peer address (--proxy-trusted-addresses). The 127.0.0.1:8080 publish for the CLI's admin API is untrusted, so it can't inject a cert. See mTLS login. - Paths. Traefik's default path handling stays on (sanitizePath, decoding of unreserved %XX). Encoded /, \, ; and %00 are allowed through because apps such as GitLab and Nextcloud use them. group-gate's path_groups matching therefore normalises the path itself and denies encoded slashes and NULs that survive one decode. path_groups checks also deny a # in the URI or an encoded one in the path.

Attribute headers¶

On every request group-gate allows (/ and /authenticated, app and core subdomains alike) it also returns X-Forwarded-Attr-<Header-Name> for the signed-in user's shared custom fields, read from the Hub's user-attributes.json in hub_data (contract §4.1 / §5):

  • control characters (0x00–0x1F, 0x7F) are stripped, and values over 1 KB are dropped and logged
  • then % → %25 and , → %2C in every value (so Doe, Jane stays one value; apps percent-decode each item), and the values are joined with ,. Non-ASCII is sent as UTF-8 bytes
  • field names must match ^[a-z][a-z0-9]*(_[a-z0-9]+)*$ (at most 31 characters) and header names ^[A-Za-z0-9]+(-[A-Za-z0-9]+)*$; a field with an invalid name or header name is skipped (logged), the others still get their headers
  • a missing or corrupt file (logged) means no attribute headers, never a deny. Two fields on one header (compared case-insensitively) make the file corrupt

portcullis-groups forwards them with authResponseHeadersRegex: ^X-Forwarded-Attr-. A headers middleware can only delete headers by exact name (and the field names are the Hub's), so client-sent X-Forwarded-Attr-* are deleted by the same regex on every forwardAuth middleware (portcullis-auth, -auth-console, -groups, -self, -public-guard): Traefik removes all request headers matching it before copying the auth server's. Public routers therefore get none, and _ aliases are dropped by the entrypoints (aliasHeadersStrategy). CI sends forged ones through the gated and public test routers.

Routers with no forwardAuth middleware (keycloak, keycloak-resources, lldap (redirect only), vault-ui, enroll-invite, and in the app overlays headscale, netbird-*, docs) do not strip client-sent X-Forwarded-Attr-*. Their backends must never trust those headers (none of them reads them).

Sessions, temporary memberships and the people directory¶

  • Temporary memberships. The policy file (version 4, the only version group-gate serves) lists expiring {user, group, at} entries. group-gate treats a membership as absent once now >= at (for the subdomain and path-group checks and in the X-Auth-Request-Groups it returns), whatever the token says, so expiry holds even while the Hub is down. A malformed entry denies (fail closed). The access token still names the expired group, so when group-gate strips a membership it withholds Authorization and X-Forwarded-Access-Token (both are portcullis-groups authResponseHeaders, so Traefik deletes them). Otherwise it echoes them unchanged: apps keep the token, and the Keycloak console behind portcullis-auth-console keeps its own bearer. A file without version denies as well; only a missing file means "nothing published".
  • Session re-validation. Forward-auth sessions are re-validated every minute (OAUTH2_PROXY_COOKIE_REFRESH=1m, a legacy option that still applies with --alpha-config): once the session cookie is a minute old, oauth2-proxy redeems the refresh token with Keycloak. A Keycloak logout or a session the Hub revokes (membership removal) then fails the refresh and ends access, and changed groups reach group-gate, within about a minute. The refresh also ends forward-auth sessions at Keycloak's SSO session limits (8 h idle, 12 h max); the 168 h cookie lifetime (cookie_expire) is only an upper bound.
  • people.<domain> (the Hub's directory listener :8889, contract §5.1) is open to any signed-in user: people=* in group-gate-map.conf (* is valid only there; in the policy file's groups it is ignored, in path_groups it is malformed). It has the admin Hub's chain (client-headers, portcullis-auth, portcullis-groups, hub-proxy-secret, security-headers), and the Hub checks permissions per request and registers no app, policy or Docker endpoint there.

Routing rules around Keycloak and oauth2-proxy¶

  • oauth2-proxy's endpoints (/oauth2/start, /oauth2/callback, /oauth2/sign_out) are routed only on auth.<domain>. A host-less PathPrefix(/oauth2/) router cannot carry the tiers' TLS options, and Traefik answers 421 on it. group-gate's step-up page therefore sends the browser to https://auth.<domain>/oauth2/start?acr_values=…&rd=<app>. CI rejects router rules without Host(.
  • Keycloak's /admin and /realms/master router uses portcullis-auth-console: the same forward-auth, minus Authorization in authResponseHeaders. The admin console sends its own bearer token to the admin API; portcullis-auth would replace it with the forward-auth session's token ("You do not have permission to access this resource").

Setup links (enroll)¶

enroll-invite (enroll.<domain>/invite/*) is the only enroll router without forward-auth.

  • The token is 256 bit, stored as SHA-256, single use, bound to one LLDAP user, valid 72 h (max 7 days) and revoked by a newer link. GET only shows it (link previews must not burn it); the same-origin POST redeems it.
  • The identity provider. enroll then acts as the hidden identity provider portcullis-invite. Keycloak shows it only for kc_idp_hint=portcullis-invite, and its first-login flow links the existing LLDAP user and never creates one. The flow uses a 10-minute HttpOnly redemption cookie scoped to /invite/, a 60 s single-use code bound to the broker redirect URI and the PKCE challenge, and an ES256 id_token.
  • Unrouted ports. Its token / JWKS port (8445) and the Hub's invite API (8444, bearer secret) are not routed by Traefik. ./portcullis invite (the CLI, through docker exec) uses a loopback-only listener (8446), the only way to invite an administrator.
  • Admins only through the CLI. The Hub API refuses admin, portcullis-hub and every member of lldap_admin, lldap_password_manager and the core-console groups of group-gate-map.conf (LLDAP group lookup, fails closed), so a leaked API secret cannot take over an admin account. The check is repeated for API-made invites at redeem, at the authorization code and at the token exchange: a user promoted to lldap_admin after the invite was made is refused, and their pending API invites are cancelled.
  • Passkey required. The invite session is LoA 2 / amr hwk and cannot finish without the passkey registration (webauthn-register-passwordless, added when the link is redeemed by enroll's service account portcullis-enroll, realm-management view-users + manage-users). enroll already held the LLDAP admin bind and Vault signing rights, so this adds no new class of power to it.
  • Re-invites. A re-invite of a user who already has keys adds one more (spare). ./portcullis invite <user> --replace-keys (lost or stolen key) deletes the user's WebAuthn credentials and sessions first.

Service accounts and public routers¶

  • The Hub's LLDAP account. The Hub logs in to LLDAP as portcullis-hub (lldap_admin; LLDAP 0.6.3's lldap_password_manager cannot create users or groups). It could already start arbitrary containers through its socket proxy, so this is no new trust (contract §9.1). The account cannot sign in: Keycloak's federation filters it out ((!(uid=portcullis-hub))) and group-gate denies it (GATE_DENY_USERS).
  • Public guard. Public exceptions (the Hub's portcullis-public-<app> routers) have no forward-auth: nothing is signed in and no identity header is passed (the Hub's strip middleware deletes client copies). Their first middleware, portcullis-public-guard@docker (group-gate /public-guard), returns 403 unless the policy file (version 4) publishes the subdomain in public_paths, the normalised path is inside one of its patterns (prefix / exact / static files; encoded /, \, NUL or # denied, and so is any # in X-Forwarded-Uri: browsers never send fragments), and the request carries none of Authorization, Proxy-Authorization, the app's credential_headers (also in _ form), credential_cookies or credential_query. Cookie and query names are compared case-insensitively after PHP's mangling (main/php_variables.c php_register_variable_ex: leading spaces dropped, /. → _, name[...] is name, an unclosed [ → _, NUL ends the name), both raw and percent-/+-decoded; names that are not valid UTF-8 (overlong forms) are refused. It never returns identity headers. See Public exceptions.
  • Logs. The guard's logs (like group-gate's path denials) show the path with token-like segments masked as <token> and query parameter names only. Never share tokens, query values, cookies or credentials.

Hub proxy secret¶

The Hub has no login of its own. Every request except GET /healthz must carry X-Portcullis-Proxy-Secret equal to HUB_PROXY_SECRET (at least 32 characters, compared in constant time). Otherwise the Hub answers 403, and it refuses to start without the variable.

./portcullis init generates the secret. The core router injects it with the hub-proxy-secret@docker headers middleware, placed after portcullis-auth and portcullis-groups. So the secret is never sent to oauth2-proxy or group-gate, and only requests that passed forward-auth and the lldap_admin check carry it. A container that reaches the Hub directly on the portcullis network can't spoof X-Forwarded-User without the secret.

To rotate it, empty HUB_PROXY_SECRET in .env and run ./portcullis upgrade.
