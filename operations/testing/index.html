Testing & CI¶

Each repository has its own GitHub Actions CI. Core tests the stack itself, the templates repo tests every template against a pinned core version, and the Hub tests and signs its image.

Repo Workflow Jobs
core (porelli/portcullis) .github/workflows/ci.yml, release.yml unit-tests, build-and-test, e2e, e2e-instances, e2e-signin, e2e-settings, e2e-folders, e2e-filesharing, e2e-mail, e2e-fxa, e2e-ai, e2e-podman, e2e-vpn, e2e-k3s, e2e-servers, e2e-servers-podman, e2e-ssh; release: preflight → ci (reusable ci.yml) → release
templates (porelli/portcullis-templates) lint.yml, test-apps.yml, docs-dispatch.yml lint; gate → changes → fetch-core (+ app-images on push to main) → test; dispatch
Hub (porelli/portcullis-hub) build.yml test, build
Keycloak image (porelli/portcullis-keycloak) build.yml test, vectors, smoke, publish
docs (porelli/portcullis-docs) deploy.yml deploy (scripts/check-branding.sh, zensical build --strict, publish to gh-pages)

Core CI¶

Runs on pushes to main, on pull requests, and as a reusable workflow (workflow_call) from release.yml. Secrets are not configured in the workflow: ./portcullis init --env-only generates them into .env, exactly as on a real install. Every step drives the stack through ./portcullis.

  • tests/test_e2e_fsops.py (step "e2e helper unit tests"). It runs with the same venv's interpreter, and needs nothing but the standard library. It tests run_op from tests/e2e/e2e_fsops.py, the module e2e_filesharing.py takes it from, against a fake Hub API. No stack, network or Playwright is involved:

    • a busy 409 whose record is the Hub's own running restart is waited for, polled by that restart's op_id. If the restart ends ok, the operation is sent exactly once more; if it ends failed, the test fails with its record.
    • any other 409 fails at once: another op, a restart that is no longer running, plain text, or a second 409 after the resend.
    • a 202 whose poll isn't the op's own ?op_id= record fails, and so does a poll that answers another op.
    • every failure message is scrubbed: a password or NT hash in a record never reaches the output.

  • tests/test_e2e_mailcheck.py (step "e2e helper unit tests (e2e_mailcheck)"). Same venv, standard library only. It tests the pure helpers e2e_mail.py takes from tests/e2e/e2e_mailcheck.py:

    • network_retries: a browser step is retried only after Chromium aborted it on a network change on the runner (net::ERR_NETWORK_CHANGED, raised by page.goto itself or left as a chrome-error:// page). It makes at most 4 attempts, notes each retry and waits between them. Any other failure is raised at once.
    • switch_voided_problem: after a provider switch, every row is voided with exactly "the mail server changed on : create a new mail password" for an allowed date, and every required label is there. active, provider_changed as a status, another reason, another date or a missing row is named.
    • navigate: page.goto / page.reload through network_retries (checked with a fake page: a raised abort, a chrome-error:// page, the reload, the bound, another error not retried).
    • mail_status_view / sync_problem: ./portcullis mail status --json is read at exit 0 and 1 (1 only says a check is a Problem); exit 2, no JSON, or a document whose problem disagrees with the exit is a failed read. The sync has converged when the provider is wired, reachable, owes no void, isn't held, and has applied the Hub's generation.
    • confirm_phrase / pending_uuids: the phrase the Hub's 400 asks to be typed (also inside a JSON error body), and the pending removal's uuids. A missing, confirmed, empty or blank-uuid pending removal fails.
    • admin_view_problems: the read-only mail admin view's flow as the browser saw it (method, status, URL per response). Every step of ADMIN_VIEW_STEPS (the Hub's POST /api/mail/admin-view, the start page and its script, the ticket's POST /portcullis/open, /admin/, /api/discover/, /login, POST /auth/token, POST /jmap) answered below 400 at least once, and no 421 or 403 anywhere; a missing or failed step, or a 421 / 403, is a problem. URLs are reported without their query.

e2e-fxa (Firefox Sync + own accounts)¶

e2e-mail's stack (the same start script, with the templates repo's firefox-sync-fxa added to the Hub's source, same-named templates branch) and its remote Stalwart, where every person's mailbox is (remote.test): each code the Hub or the accounts server sends crosses the path it takes on a server, through Portcullis's submission listener (the sender's password, STARTTLS required), its outbound queue and the remote's MX, which checks DKIM. Two things make the runner behave like a server:

  • The server's names resolve for containers. .github/ci/e2e-fxa-dns.sh (first, before any other container) runs a CoreDNS container published on the runner's address :53, which answers every name under the domain with that address (where Traefik's 443 and the mail ports are published), forwards every other name upstream, and is Docker's DNS server. fxa-auth and the Hub reach mail.<d>:587, the admin UI reaches Keycloak at auth.<d>; the runner itself uses /etc/hosts with the same address.
  • Mail's certificate is trusted like a public one. .github/ci/e2e-fxa-trust.sh adds Pebble's root to the runner's system store and runs ./portcullis config apply --bundle-only, the documented way for a mail server with its own CA: fxa-auth and the Hub check the certificate against certs/ca-bundle.crt. On a server with ACME_STAGING=true the bundle carries Let's Encrypt's staging root X1 in addition to the system CAs; mail-cert's certificate is always ECDSA, and staging issues those from its X2 hierarchy, so check STARTTLS against the bundle after each issue. Switching ACME_STAGING back to false drops the staging root while mail's certificate stays the staging one until its renewal (below 30 days; ./portcullis mail cert has no forced re-issue): until then no code goes out.

Caching¶

Core CI caches what it safely can. Caches are written only on pushes to main.

  • Infra and monitoring images: cached by the local composite action .github/actions/cached-images.
    • The cache key is the runner image (ImageOS: ubuntu24, ubuntu26, …; self-hosted on the builder) and a hash of each job's pinned image list. Refs without a digest are refused. A tarball saved by one image's Docker doesn't load reliably on another's, so jobs on 24.04 and 26.04 never share one.
    • After docker load, every name set by the tarball is removed. Each ref is then re-pulled by its pinned digest (with retry and backoff), so the engine reuses a loaded image only if its content-addressed ID matches the registry's config digest.
  • enroll and group-gate images: buildx layer cache (type=gha).
  • Go: module and build cache through setup-go, with go mod verify.
  • Python: pip and Playwright browsers, cached on the runner image (ImageOS, as above: Playwright's browser builds are per distro) and the pinned requirements file (group-gate/requirements.txt has --require-hashes).
  • Runner images: every job that installs Playwright's system packages (playwright install-deps) runs on ubuntu-24.04; the 26.04 image lacks some of its font packages. e2e-podman, e2e-k3s and e2e-servers* stay on ubuntu-26.04 (e2e-servers installs Playwright's deps there, which resolve).

The revocation check waits up to 180s, because Vault rebuilds delta CRLs at most once a minute.

Releases (release.yml)¶

Runs on v* tags:

  1. preflight checks four things:
    • The tag is vMAJOR.MINOR.PATCH and CHANGELOG.md has its ## [X.Y.Z] section.
    • The HUB_IMAGE default in docker-compose.yml is ghcr.io/porelli/portcullis-hub:A.B.C@sha256:…, where vA.B.C is a published (non-draft, non-prerelease) Hub release and the tag still resolves to that digest.

Auto-merge¶

Core, the Hub and the templates share one auto-merge workflow, .github/workflows/dependabot-automerge.yml. Its logic lives in .github/automerge/automerge.sh, which is identical in all three repos and tested by .github/automerge/test.sh. The workflow runs after the required workflows finish on a Dependabot PR and never checks out PR code:

  • Patch, minor and digest-only updates are squash-merged once every required workflow passed on the PR's head commit. The PR must be Dependabot's own single, GitHub-signed commit.
  • Majors (or updates of unknown type) get the major-update label and stay open.
  • Pre-releases are closed.
  • Red CI opens an update-failed issue.

A merge that fails although CI passed gets at most one re-attempt. Only GitHub's "Base branch was modified" error is re-attempted. It happens when another PR merged at the same moment. The workflow waits about 10 seconds, then tries the merge once more at the same tested commit. Anything else, such as an HTTP 5xx, is not retried. If the merge still fails, the run fails and its error names the cause and the command to retry by hand:

gh workflow run dependabot-automerge.yml -f pr=<n> -f dry_run=false

Run it from a checkout of the repo, or add -R porelli/<repo>. Check the PR first: a 5xx can still have merged it. Leave out -f dry_run=false to see the decision without acting on it.

The workflow doesn't ask Dependabot to rebase. Dependabot ignores @dependabot rebase comments posted with the workflow's GITHUB_TOKEN (or by any GitHub App) and replies "only users with push access can use that command".

Running a CI job on a Docker host (run-job.sh)¶

.github/ci/local/run-job.sh <job> runs one ci.yml job on a Linux host with Docker (the shared dev builder), step by step as GitHub's runner does, and cleans up after itself:

.github/ci/local/run-job.sh build-and-test                  # main, fresh clone from GitHub
.github/ci/local/run-job.sh e2e-mail --scenario 4           # one scenario (+ its setup)
.github/ci/local/run-job.sh e2e-signin --ref mybranch       # a pushed branch
.github/ci/local/run-job.sh e2e-ai --local ~/w/portcullis   # a working tree, uncommitted changes included
.github/ci/local/run-job.sh e2e --keep                      # keep the container to look around
.github/ci/local/run-job.sh --cleanup <container>           # …then remove it
  • Isolation. Every run is its own privileged Ubuntu 24.04 system container pcci-<job>-<id> (.github/ci/local/Dockerfile: systemd, its own dockerd, user runner 1001 with passwordless sudo, Docker CE + buildx + compose, jq, yq, shellcheck, python3, gcc, Node.js LTS, Playwright's system packages) on its own bridge network (10.250.<n>.0/24), 4 CPUs / 16 GB like a GitHub runner (--cpus / --memory); /tmp, /srv and the workspace are volumes (ext4 with ACLs, as on GitHub) and dockerd's data-root is /var/lib/docker-store/docker (a container's mountinfo names …/docker/containers/<id>/, as the Hub's tests expect). Every job and step timeout-minutes is multiplied by --timeout-factor (default 1.5: ci.yml's limits are sized for a fresh GitHub runner). The job's compose project, its fixed networks (172.30/172.31), published ports, /etc/hosts lines and /tmp files are the container's own, so several runs (and other work on the host) never collide; the compose project inside stays portcullis because the steps name portcullis_* volumes. The checkout is a fresh clone in ~/w/ci-local/<id>/, copied into the workspace volume at /home/runner/work/portcullis/portcullis. Afterwards the container, its network and its volumes are removed and the clone deleted; run.log and uploaded artifacts stay in ~/w/ci-local/<id>/ (pruned after 7 days).
  • Steps. .github/ci/local/steps.py reads the job from ci.yml (so it can't drift) and runs it like Actions: workflow / job / step env with ${{ }} expressions, if: (default success(), always(), failure()), Actions' default shells, working-directory, timeout-minutes, continue-on-error, GITHUB_ENV / GITHUB_OUTPUT / GITHUB_PATH / GITHUB_STEP_SUMMARY, step outputs, and the local composite actions (cached-images, hub-image, keycloak-image). The event is a workflow_dispatch of the checked-out branch (nothing saves caches; same-named Hub / Keycloak / templates branches are used as in CI). uses: steps that need GitHub are emulated: actions/checkout (the workspace is already there; another repository is cloned), actions/setup-go (Go from go.dev, sha256-checked), actions/cache* (always a miss), actions/upload-artifact (copied to the run directory), docker/setup-buildx-action (no-op), docker/build-push-action (docker buildx build --load, no gha layer cache, never a push).
  • Caches. Unless --no-cache: the job's image store (pcci-cache-<job>-* volumes; one run of a job at a time uses it, a concurrent one gets a throwaway store) — sanitized before every run: no container, volume or network survives, and every image name not backed by a registry pull of that repository is removed — and the shared pip / Playwright / go-build and Go module caches. The Go toolchain is downloaded every run.
  • Not here: e2e-podman (stops the runner's Docker) and e2e-k3s (installs k3s; use .github/ci/e2e-k3s-local.sh container). The Actions layer cache (type=gha) and artifact service don't exist locally.

The builder (Ubuntu 24.04) also has rootless Podman for user pcpodman (sudo -iu pcpodman; DOCKER_HOST is its user socket, so docker / docker compose talk to Podman; netavark, pasta, slirp4netns; Ubuntu's Podman 4.9 — CI's e2e-podman runs 26.04's 5.x), Node.js LTS (the Hub's web tests) and docker:dind works privileged (e2e-servers' dind workers).

Single-scenario reruns (scenarios)¶

gh workflow run ci.yml --ref <branch> -f jobs=e2e-mail -f scenarios="4 members_only_list" runs only those scenarios of the e2e runners (tests/e2e/*.py), plus their setup; empty = all. E2E_SCENARIOS (the workflow's env) carries it to the runners, and run-job.sh --scenario sets the same. A scenario's name comes from its check() name: the text before the first : (or the whole name), parenthesised parts dropped, split on , + /, with an optional leading number — "4 mail_password_flow" is 4 and mail_password_flow, "cross_domain_sso: …" is cross_domain_sso; a check whose name gives no identifier ("alice, bob and carol: setup link → passkey → portal") is setup and always runs, as do setup, seed, finally and what a runner declares with scenarios.always() (e2e_ai's ai_on, e2e_instances' alice). A named scenario also pulls in the scenarios whose checks set the state keys it needs() (read from the source with ast, transitively); state built any other way isn't seen — such a scenario fails closed with "needs …": name that one too. python3 tests/e2e/scenarios.py list names every scenario; jobs-input fails the run on a name none of the chosen jobs' runners knows (scenarios.py check), and each runner fails at import on a name no runner knows. Only the Python runners' checks are filtered: the job's shell steps (stack start, backups, shell assertions) still run.

The self-hosted builder runner (runner: builder)¶

gh workflow run ci.yml --ref <branch> -f runner=builder [-f jobs=…] (core) or gh workflow run build.yml --ref <branch> -f runner=builder (Hub: the test job only; build — GHCR push, cosign's OIDC token — never leaves GitHub) runs the jobs on the dev builder's ephemeral runner instead of ubuntu-latest. runs-on resolves to [self-hosted, linux, x64, pc-builder] only when github.event_name == 'workflow_dispatch' and the input is builder; push, pull_request and workflow_call (releases) always get GitHub's runners, and e2e-podman / e2e-k3s never use it.

On the builder (.github/ci/local/runner/, installed by sudo .github/ci/local/runner/install.sh): user ghrunner (system user, no password, no sudo, in the docker group — root-equivalent on the host), pcci-runner@portcullis.service and pcci-runner@portcullis-hub.service (runner-loop.sh): each start registers one ephemeral runner (pc-builder-portcullis / pc-builder-portcullis-hub, repo level, label pc-builder, --ephemeral) inside a fresh privileged job container (the run-job.sh image with the official actions/runner), takes one job, and is removed with the container; systemd starts the next. Every job gets a fresh workspace, /srv, image store and tool cache; only pip / Playwright / go-build and the Go module cache (GOFLAGS=-mod=readonly) persist per repo. The runner's ACTIONS_RUNNER_HOOK_JOB_STARTED hook (job-started-hook.sh) refuses — before any step — every job that isn't a workflow_dispatch of that repo's ci.yml / build.yml on a branch, dispatched (actor and triggering actor) by the repository owner: the privileged container and the shared caches are acceptable only under that rule. Both repos require approval for fork pull-request workflows from all outside contributors. A builder job never writes GitHub's shared Actions cache (GitHub-hosted runs restore it): every cache-writing step of a builder-switchable job carries !(github.event_name == 'workflow_dispatch' && inputs.runner == 'builder') or writes only on a push (setup-go's cache, actions/cache/save, build-push's cache-to, cached-images' save), checked by tests/lint_builder_cache.sh (core unit-tests; a byte copy runs in the Hub's test job). Registration tokens come from /etc/pcci-runner/gh-pat (a fine-grained token for the two repositories with Administration: read and write; unattended) or, without it, a token dropped into /var/lib/pcci-runner/tokens/<repo>.json (gh api -X POST repos/porelli/<repo>/actions/runners/registration-token, one registration each). Removal: sudo .github/ci/local/runner/uninstall.sh, then delete the registrations (gh api repos/porelli/<repo>/actions/runners → gh api -X DELETE repos/porelli/<repo>/actions/runners/<id>).

Triggers: push to main, pull requests to main (from forks too: core is public and no job uses a secret), and manual workflow_dispatch (inputs pr, ref, apps; apps = all tests every template). Dependabot's image bumps are pull requests, so each runs the tests of the app it touches. Per-app sign-in e2e¶

tests/e2e/app_signin.py (Playwright with a CDP virtual WebAuthn authenticator, like core's e2e job) proves a real person can sign in to each app through Portcullis and gets the right role. Driven by the manifest's tests.signin, per app:

  1. LLDAP users without passwords: e2eadmin (access + admin group), e2emember (access group), e2eoutsider (no group);
  2. what the Hub would do: the template's Keycloak clients (secret = the app's generated env, which the workflow creates once for the shell test and the e2e), the group-gate policy file (access_group per host, auth.admin_paths; its version is read from core's group-gate);
  3. the app started with tests/lib.sh compose_up, containers ready: every service without compose profiles: and those of the selected profiles (COMPOSE_PROFILES when set — * = every profile —, else the profiles the setup choices' defaults start, as the Hub does; compose_up starts the same);
  4. per user, portcullis invite <user> --to https://<host><path> --json opened in Chromium: passkey registration, then the app's own sign-in (its SSO button, the OIDC / SAML round trip, or forward-auth);
  5. results: member signed in with its username and not admin, admin has admin rights, outsider refused (group-gate's 403 or the app's denial); any password field fails unless the manifest documents it; an outsider refusal when nobody could sign in is reported inconclusive.

expected_fail marks known failures: reported, not fatal, only when the failure matches the entry's match (and not its not_match) in that check's own evidence: its detail, the pages its flow saw, the app's logs since its flow started. A flow the test broke (password field, Keycloak/enroll or browser error, never on the app) or an exception fails, and a marked check that passes fails the run so the marker is removed. Where group-gate decides (forward-auth, header-auth, and the login-path gates of GitLab, LiteLLM and Vaultwarden) only group-gate's own refusal counts for the outsider: its HTTP 403, its "not authorized" page and its DENIED user=… host=… log line. Each setup link must register exactly one passkey. Today: the outsider check of the native-OIDC apps with no group restriction of their own that let every test user in (Headscale/Headplane, Immich): with the Hub, its Keycloak access role (keycloak_access_role) refuses outsiders at Keycloak, but CI has no Hub (the test registers plain clients), so the role is not applied there; the member check of the apps that admit only their first user (the owner) and users the owner adds or approves (Actual Budget, NetBird); the member and admin checks of Nextcloud, whose HTTP client refuses a local TLD (.local) or private address for Keycloak (match: "violates local access rules"; its outsider check is then inconclusive) — the test never widens an app's access to make a check pass. skip: docs (public), Plex (custom, plex.tv). Each run starts the app from fresh volumes.

CI stand-ins for public DNS: every app hostname is a network alias of Traefik on portcullis-proxy (apps reach auth.<domain> for OIDC discovery and the token exchange) and is in the runner's /etc/hosts (the browser). Chromium trusts core's root CA through an NSS database. Results go to the job summary; on failure the e2e-<app> artifact holds every step's screenshot and HTML, a Playwright trace per user (playwright show-trace), the app's container logs and core's logs.

Weekly (and on dispatch), tests/craft-releases.sh bumps each Craft template's pinned web release (${CRAFT_VERSION:-…} / ${CRAFT_SHA256:-…}) to the latest release of storytold/<app>, once the GitHub asset digest, SHA256SUMS.txt and the download agree, and opens one PR per app on craft/<app>-<ver>. It uses only GITHUB_TOKEN (contents, pull-requests, actions: write). PRs opened with that token start no pull_request workflows, so the script dispatches Test Apps (pr=<n>, apps=<app>, core ref from the PR's base) and Lint (on the branch) for each PR it opens; workflow_dispatch is the one event GITHUB_TOKEN may start. The Test Apps run is dispatched on the base branch, so its check attaches to the base commit, not the PR: the script links the run in the PR body.

AI support in the app tests. gitea.sh, grafana.sh, nextcloud.sh and homeassistant.sh run their mint / revoke / on_change hooks the way the Hub does (argv verbatim, JSON on stdin, split output) and check that a credential never reaches an argv or a log. nextcloud.sh starts the companion and checks per-person identity (one person's app password sees only their files; no credential, nothing; a bad one, 401). grafana.sh checks the trust network (internal, exactly Grafana and the companion, Grafana's allowlist without the gateway, broadcast and its own address) and that a spoofed X-Forwarded-User from elsewhere on portcullis-proxy isn't signed in.

Setup choices in the app tests. tests/lib.sh compose_up selects the compose profiles the setup choices' defaults start (COMPOSE_PROFILES, as the Hub writes it; a test picks another choice by exporting COMPOSE_PROFILES and the option's variable itself), and compose_down takes down every profile (--profile '*'). nextcloud.sh runs its full suite on the default database, PostgreSQL, then installs once more on MySQL / MariaDB and on SQLite: each engine is the one Nextcloud uses (dbtype, dbhost, a user_oidc row it reads back), only that engine's database server runs, and a marker written before the whole project goes down is read back after it comes up again. ai-chat.sh renders librechat.yaml from ai-providers.json (secrets only as ${VAR} references, a refused file fails closed), checks the access-group restriction and the MCP OAuth callback. write_ai_providers_override (below) emulates the Hub's delivery to an AI page.

Running workflows locally with act¶

act runs GitHub Actions workflows locally in Docker:

act -l -W .github/workflows/test-apps.yml                     # list jobs (templates repo)
act -j lint -W .github/workflows/lint.yml                      # static checks, no secrets
act -W .github/workflows/test-apps.yml                         # integration (no secrets needed)
act -W .github/workflows/ci.yml                                # core CI (core repo)

The first run downloads the runner images, which can take a few minutes.
