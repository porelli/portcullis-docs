Testing & CI¶

Each repository has its own GitHub Actions CI. Core tests the stack itself, the templates repo tests every template against a pinned core version, and the Hub tests and signs its image.

Repo Workflow Jobs
core (porelli/portcullis) .github/workflows/ci.yml, release.yml unit-tests, build-and-test, e2e, e2e-instances, e2e-signin, e2e-settings, e2e-folders, e2e-filesharing, e2e-ai; release: preflight → ci (reusable ci.yml) → release
templates (porelli/portcullis-templates) lint.yml, test-apps.yml, docs-dispatch.yml lint; gate → changes → fetch-core (+ app-images on push to main) → test; dispatch
Hub (porelli/portcullis-hub) build.yml test, build
Keycloak image (porelli/portcullis-keycloak) build.yml test, vectors, smoke, publish
docs (porelli/portcullis-docs) deploy.yml deploy (scripts/check-branding.sh, zensical build --strict, publish to gh-pages)

Core CI¶

Runs on pushes to main, on pull requests, and as a reusable workflow (workflow_call) from release.yml. Secrets are not configured in the workflow: ./portcullis init --env-only generates them into .env, exactly as on a real install. Every step drives the stack through ./portcullis.

  • tests/test_e2e_fsops.py (step "e2e helper unit tests"). It runs with the same venv's interpreter, and needs nothing but the standard library. It tests run_op from tests/e2e/e2e_fsops.py, the module e2e_filesharing.py takes it from, against a fake Hub API. No stack, network or Playwright is involved:

    • a busy 409 whose record is the Hub's own running restart is waited for, polled by that restart's op_id. If the restart ends ok, the operation is sent exactly once more; if it ends failed, the test fails with its record.
    • any other 409 fails at once: another op, a restart that is no longer running, plain text, or a second 409 after the resend.
    • a 202 whose poll isn't the op's own ?op_id= record fails, and so does a poll that answers another op.
    • every failure message is scrubbed: a password or NT hash in a record never reaches the output.

    The Python unit tests are plain unittest scripts, run one by one; CI has no pytest. Locally, python3 -m pytest -q tests/ collects the same files.

e2e (browser)¶

tests/e2e/e2e_login.py runs Playwright Chromium (pinned in tests/e2e/requirements.txt) with a CDP virtual WebAuthn authenticator against the full chain: Traefik → oauth2-proxy → Keycloak (LLDAP users, WebAuthn, X.509) → group-gate. A whoami test app has three hosts: app. (group users_e2e, /admin → admin_e2e, the default template Standard), hwk. (template any[security_key]) and mtls. (template any[yubikey_cert]). With no Hub in this job, the workflow writes policy file v6 and signin-keycloak.json itself; the latter's trust list is the CI fixture tests/e2e/fixtures/virtual-authenticators.json: Chromium's virtual CTAP2 authenticator (AAGUID 01020304-0506-0708-0102-030405060708, packed attestation with a self-signed "Batch Certificate", backup-eligible 0) as a security_key with that certificate as its root, so the virtual key registers as a security key (Keycloak's realm asks for direct attestation). The jobs that run the Hub (e2e-instances, e2e-signin, e2e-settings, e2e-folders, e2e-filesharing, e2e-ai) start it with HUB_DEV=1 and HUB_SIGNIN_EXTRA_AUTHENTICATORS=/run/portcullis/signin/extra-authenticators.json through their CI-only compose override, which mounts the same fixture read-only there (e2e-signin mounts a copy's directory instead, which its test rewrites) (contract §8.1 "Extra entries", development only), so their virtual keys are security keys too (Strong on hub / people). Every setup-link sign-in in them walks the step-up page with the shared passkey_flow helper of e2e_login.py; every caller states how many step-up pages it expects (one after a setup link, none for a later sign-in), and one more fails at once.

Caching¶

Core CI caches what it safely can. Caches are written only on pushes to main.

  • Infra and monitoring images: cached by the local composite action .github/actions/cached-images.
    • The cache key is a hash of each job's pinned image list. Refs without a digest are refused.
    • After docker load, every name set by the tarball is removed. Each ref is then re-pulled by its pinned digest (with retry and backoff), so the engine reuses a loaded image only if its content-addressed ID matches the registry's config digest.
  • enroll and group-gate images: buildx layer cache (type=gha).
  • Go: module and build cache through setup-go, with go mod verify.
  • Python: pip and Playwright browsers, cached on the pinned requirements file (group-gate/requirements.txt has --require-hashes).

The revocation check waits up to 180s, because Vault rebuilds delta CRLs at most once a minute.

Auto-merge¶

Core, the Hub and the templates share one auto-merge workflow, .github/workflows/dependabot-automerge.yml. Its logic lives in .github/automerge/automerge.sh, which is identical in all three repos and tested by .github/automerge/test.sh. The workflow runs after the required workflows finish on a Dependabot PR and never checks out PR code:

  • Patch, minor and digest-only updates are squash-merged once every required workflow passed on the PR's head commit. The PR must be Dependabot's own single, GitHub-signed commit.
  • Majors (or updates of unknown type) get the major-update label and stay open.
  • Pre-releases are closed.
  • Red CI opens an update-failed issue.

A merge that fails although CI passed gets at most one re-attempt. Only GitHub's "Base branch was modified" error is re-attempted. It happens when another PR merged at the same moment. The workflow waits about 10 seconds, then tries the merge once more at the same tested commit. Anything else, such as an HTTP 5xx, is not retried. If the merge still fails, the run fails and its error names the cause and the command to retry by hand:

gh workflow run dependabot-automerge.yml -f pr=<n> -f dry_run=false

Run it from a checkout of the repo, or add -R porelli/<repo>. Check the PR first: a 5xx can still have merged it. Leave out -f dry_run=false to see the decision without acting on it.

The workflow doesn't ask Dependabot to rebase. Dependabot ignores @dependabot rebase comments posted with the workflow's GITHUB_TOKEN (or by any GitHub App) and replies "only users with push access can use that command".

Loads the cached infra and app images as untrusted: removes every name a tarball sets, then binds each image (core's and the app's) with a docker pull of its tag@sha256 pin. The pull checks the manifest against the pinned digest and reuses a loaded image only if its ID (the hash of its config, which pins every layer) is the one that manifest names; otherwise it downloads the image fresh. Boots infra like core's own CI: every secret generated by portcullis init --env-only (the workflow sets none, since the shell environment would override .env), Keycloak with its production start command, setup through the core CLI (vault init, pki setup --with-server-cert, config apply --bundle-only, keycloak configure, oidc register). Checks Traefik got its static IP and that forward-auth redirects an unauthenticated request to auth.<domain>, then runs the app's shell test and its sign-in e2e. Uploads e2e-<app> (screenshots, page HTML, traces, logs) on failure

Every job has a read-only contents: read token. The workflow deliberately does not use pull_request_target, which would run fork code with a write token.

Fork PRs get the full integration tests automatically. A maintainer can re-run one with Actions → Test Apps → Run workflow, pr = <number>. That run tests exactly the PR's head commit, and aborts if the head moved.

.core-ref holds the core ref the templates are tested against: a tag such as v1.4.0, or main during development (today: main). Changing it re-tests every template.

Per-app sign-in e2e¶

tests/e2e/app_signin.py (Playwright with a CDP virtual WebAuthn authenticator, like core's e2e job) proves a real person can sign in to each app through Portcullis and gets the right role. Driven by the manifest's tests.signin, per app:

  1. LLDAP users without passwords: e2eadmin (access + admin group), e2emember (access group), e2eoutsider (no group);
  2. what the Hub would do: the template's Keycloak clients (secret = the app's generated env, which the workflow creates once for the shell test and the e2e), the group-gate policy file (access_group per host, auth.admin_paths; its version is read from core's group-gate);
  3. the app started with tests/lib.sh compose_up, containers ready: every service without compose profiles: and those of the selected profiles (COMPOSE_PROFILES when set — * = every profile —, else the profiles the setup choices' defaults start, as the Hub does; compose_up starts the same);
  4. per user, portcullis invite <user> --to https://<host><path> --json opened in Chromium: passkey registration, then the app's own sign-in (its SSO button, the OIDC / SAML round trip, or forward-auth);
  5. results: member signed in with its username and not admin, admin has admin rights, outsider refused (group-gate's 403 or the app's denial); any password field fails unless the manifest documents it; an outsider refusal when nobody could sign in is reported inconclusive.

expected_fail marks known failures: reported, not fatal, only when the failure matches the entry's match (and not its not_match) in that check's own evidence: its detail, the pages its flow saw, the app's logs since its flow started. A flow the test broke (password field, Keycloak/enroll or browser error, never on the app) or an exception fails, and a marked check that passes fails the run so the marker is removed. Where group-gate decides (forward-auth, header-auth, and the login-path gates of GitLab, LiteLLM and Vaultwarden) only group-gate's own refusal counts for the outsider: its HTTP 403, its "not authorized" page and its DENIED user=… host=… log line. Each setup link must register exactly one passkey. Today: the outsider check of the native-OIDC apps with no group restriction of their own that let every test user in (Headscale/Headplane, Immich): with the Hub, its Keycloak access role (keycloak_access_role) refuses outsiders at Keycloak, but CI has no Hub (the test registers plain clients), so the role is not applied there; the member check of the apps that admit only their first user (the owner) and users the owner adds or approves (Actual Budget, NetBird); the member and admin checks of Nextcloud, whose HTTP client refuses a local TLD (.local) or private address for Keycloak (match: "violates local access rules"; its outsider check is then inconclusive) — the test never widens an app's access to make a check pass. skip: docs (public), Plex (custom, plex.tv). Each run starts the app from fresh volumes.

CI stand-ins for public DNS: every app hostname is a network alias of Traefik on portcullis-proxy (apps reach auth.<domain> for OIDC discovery and the token exchange) and is in the runner's /etc/hosts (the browser). Chromium trusts core's root CA through an NSS database. Results go to the job summary; on failure the e2e-<app> artifact holds every step's screenshot and HTML, a Playwright trace per user (playwright show-trace), the app's container logs and core's logs.

docs-dispatch.yml¶

On push to main it sends a templates-updated repository_dispatch to this docs repo, which regenerates the App Catalog. It needs the DOCS_DISPATCH_TOKEN secret. Without it the step is skipped with a notice, and the docs pick the change up on their daily rebuild.

craft-releases.yml¶

Weekly (and on dispatch), tests/craft-releases.sh bumps each Craft template's pinned web release (${CRAFT_VERSION:-…} / ${CRAFT_SHA256:-…}) to the latest release of storytold/<app>, once the GitHub asset digest, SHA256SUMS.txt and the download agree, and opens one PR per app on craft/<app>-<ver>. It uses only GITHUB_TOKEN (contents, pull-requests, actions: write). PRs opened with that token start no pull_request workflows, so the script dispatches Test Apps (pr=<n>, apps=<app>, core ref from the PR's base) and Lint (on the branch) for each PR it opens; workflow_dispatch is the one event GITHUB_TOKEN may start. The Test Apps run is dispatched on the base branch, so its check attaches to the base commit, not the PR: the script links the run in the PR body.

AI support in the app tests. gitea.sh, grafana.sh, nextcloud.sh and homeassistant.sh run their mint / revoke / on_change hooks the way the Hub does (argv verbatim, JSON on stdin, split output) and check that a credential never reaches an argv or a log. nextcloud.sh starts the companion and checks per-person identity (one person's app password sees only their files; no credential, nothing; a bad one, 401). grafana.sh checks the trust network (internal, exactly Grafana and the companion, Grafana's allowlist without the gateway, broadcast and its own address) and that a spoofed X-Forwarded-User from elsewhere on portcullis-proxy isn't signed in.

Setup choices in the app tests. tests/lib.sh compose_up selects the compose profiles the setup choices' defaults start (COMPOSE_PROFILES, as the Hub writes it; a test picks another choice by exporting COMPOSE_PROFILES and the option's variable itself), and compose_down takes down every profile (--profile '*'). nextcloud.sh runs its full suite on the default database, PostgreSQL, then installs once more on MySQL / MariaDB and on SQLite: each engine is the one Nextcloud uses (dbtype, dbhost, a user_oidc row it reads back), only that engine's database server runs, and a marker written before the whole project goes down is read back after it comes up again. ai-chat.sh renders librechat.yaml from ai-providers.json (secrets only as ${VAR} references, a refused file fails closed), checks the access-group restriction and the MCP OAuth callback. write_ai_providers_override (below) emulates the Hub's delivery to an AI page.

Running workflows locally with act¶

act runs GitHub Actions workflows locally in Docker:

act -l -W .github/workflows/test-apps.yml                     # list jobs (templates repo)
act -j lint -W .github/workflows/lint.yml                      # static checks, no secrets
act -W .github/workflows/test-apps.yml                         # integration (no secrets needed)
act -W .github/workflows/ci.yml                                # core CI (core repo)

The first run downloads the runner images, which can take a few minutes.
