Hub Management¶

The Hub is Portcullis's web dashboard for app templates. It lists the catalog, enables and disables apps, edits their settings and access policies, and shows status and logs. It is published as ghcr.io/porelli/portcullis-hub and run by the core docker-compose.yml (HUB_IMAGE). There is nothing to build.

Open it at https://hub.<your-domain>. It requires a Keycloak login and membership of lldap_admin.

App Catalog¶

The main view lists every template from every template source as a card:

  • icon, name and one-line description
  • auth badges:
Badge Meaning
SSO The app supports single sign-on via Keycloak (auth.sso)
Group Access group-gate restricts the app's subdomains to the users_<app> group (auth.group_access)
Group Admin The app maps the admin_<app> group to its admin role (auth.group_admin)
Method forward-auth, native-oidc, header-auth, mtls, custom or public
  • whether the app is enabled and running

Enabling an app¶

  1. Open the app card and review the details.
  2. Fill in its settings (media folders, ports, options) and, if needed, its access policy.
  3. Click Enable.

Before anything starts, the Hub refuses to enable the app if:

  • one of its host ports (from Settings or its custom override) overlaps a host port of another enabled app (HTTP 409, "port 0.0.0.0:3300/tcp already claimed by enabled app …"), or
  • one of its subdomains is already routed by another enabled app (HTTP 409, "subdomain … is already routed by enabled app …"). Every subdomain has exactly one owner, because group-gate keys groups and policies by subdomain.

It then generates the per-app .env and compose override, copies the template directory to <core>/templates/<app-id>/, registers the template's Keycloak clients (a client ID owned by another template or by nobody provable aborts the enable with HTTP 409, see Keycloak clients) and runs docker compose up. The app is recorded as enabled only after compose up succeeds. Then the Hub publishes its group, admin paths and policy to group-gate.

The Hub can't test host ports outside Docker from inside its container (a service on the host, e.g. systemd-resolved on 127.0.0.53:53), so those conflicts surface as a compose up failure. See When an operation fails.

When an operation fails¶

If enable, disable, restart or a drift action fails, the UI opens a dialog with the error, a hint where one is known, and the last 8 KiB of docker compose's output (scrollable). Values of secret-looking variables (names containing SECRET, PASSWORD, TOKEN, KEY, …, and generated ones) from the app's and core's env are replaced with [redacted]. For address already in use / port is already allocated the hint names the port and links to the app's Settings → Host Ports: change the host port, bind it to one address, or clear it (optional ports) to disable the binding, then enable again.

A failed compose up during enable is rolled back: the Hub runs docker compose down --remove-orphans for the project (volumes are kept), so no stopped containers or network stay behind. The app stays disabled, and neither the fail-closed deny entry nor a stopped_not_enabled drift item is left over. If the rollback fails too, the error says so and the leftovers show up in Drift detection (Stop & remove).

Every operation's outcome is stored per app in ${HUB_DATA_DIR}/ops/<app>.json (operation, time, ok/failed, error, hint, output tail; mode 0600), and kept until the next operation on that app. A card whose last operation failed shows "last enable failed" (or restart, …); its detail panel shows a banner, and the Logs tab, also for an app that is not enabled, shows the record above the container logs. The API:

GET  /api/templates/lastop/<app>   {op, at, ok, error?, output?, hint?, rolled_back?} or null

A failed lifecycle request (POST /api/templates/enable, /disable, /restart/<app>, /api/drift/resolve) answers with its HTTP status and a JSON body {error, op, output, hint, rolled_back}; other errors stay plain text.

Disabling an app¶

Click Disable in the app's detail panel. The Hub runs docker compose down for the project. The app is marked disabled only once that succeeds. If stopping fails, the app stays enabled and the error is shown, so you can retry instead of being left with orphaned containers. If the template is gone or its compose file is broken, the Hub falls back to docker compose -p portcullis-<id> down.

Keycloak clients are not deleted when you disable an app. Volumes are kept.

Only one lifecycle operation (enable, disable, restart) runs per app at a time. A second request while one is in progress is rejected with a "try again shortly" message.

App detail panel¶

Each enabled app has four tabs: Settings, Status, Logs and Expert. An app that is not enabled has Settings and Expert, plus Logs when its last operation failed.

Settings¶

  • The Sign-in block, only for apps whose manifest declares auth.native_login (Plex): Portcullis sign-in, then the app's own login (default; the override adds portcullis-auth@docker,portcullis-groups@docker to every router, group = the template's access_group) or App's own login only (no Portcullis), offered only if the template allows it. Choosing the latter shows a red warning; saving writes the routers without the gateway middlewares and with public@file, publishes no group for the app, logs a warning and adds an app.sign_in entry (actor, gateway -> native) to the audit log, refusals included. See Apps with their own login.
  • The access policy block, capability-aware (see What each app can enforce):
    • Inherit global default is ticked for every app without an override. While it is, the boxes are disabled and show the effective policy (global default ∩ what the app can enforce), with the TLS tier and notes: how the app enforces it (per request, at login, at the TLS handshake), and what differs from the global default, including a default the app can't enforce at all.
    • Unticked, only the factors the app supports can be checked (mTLS and WebAuthn; mTLS only for mtls apps), with any-of or all-of. The Hub refuses other factors with a 400 naming them.
    • Apps that handle their own sign-in (custom without Portcullis sign-in, public) show the block disabled: "This app handles its own sign-in".
    • There is no password factor. A stored policy that names password is normalised (never weaker) and the block says so until it is saved.
  • Settings declared in the manifest:
    • path / paths: host directories bind-mounted into a container, e.g. media libraries
    • text: free-form values
    • boolean: toggles
    • select: a dropdown of the manifest's options
  • Host ports declared in the manifest: rebind them, or clear optional ones to disable the binding.
  • The public exceptions block, only for apps whose manifest declares auth.public_access. See Public exceptions.

Saving restarts the app in the background. Clearing a text field clears the value in the app's .env.

Input validation:

  • Path settings may not contain : (Compose would read it as host:container) or newlines. Spaces, quotes and # are fine, because paths are quoted in the generated override.
  • Port bind addresses must be IP addresses (e.g. 0.0.0.0, 127.0.0.1, ::1). IPv6 is bracketed automatically.
  • No setting value may contain newlines or other control characters.

Status¶

Lists each container of the app's compose project with its state:

  • All containers running
  • Some containers not running
  • Containers stopped

The information comes from the Docker Engine API through the Hub's socket proxy.

Logs¶

Shows the app's last operation (with compose's output if it failed), then the last 100, 200 or 500 log lines of the app's containers. Use Refresh to reload.

Expert¶

Advanced tools with direct access to the compose configuration and the containers. Compose runs with three files, later ones winning:

docker compose -p portcullis-<app> \
  -f <template>/compose.yml \
  -f ${HUB_DATA_DIR}/overrides/<app>.override.yml \
  -f ${HUB_DATA_DIR}/overrides/<app>.user.yml
  1. compose.yml (read-only). The template's file as it comes from the template source. The Hub never writes it, so source syncs always fast-forward. To change routing (subdomains, routers, middlewares), change the template in its source (see Template sources).
  2. Hub override (read-only). Generated from Settings and regenerated before every compose up: bind mounts, host ports, each router's tls.options derived from the access policy, router middlewares for apps with their own login, and the public-exception router with its strip middleware when on. Never hand-edited.

  3. Custom override (editable). Your own additions, stored by the Hub per app, outside the template clone, so template syncs and updates keep it. See Custom override.

  4. Environment variables. Edit the app's own .env (stored in the Hub data directory), or add a variable. Names must match [A-Za-z_][A-Za-z0-9_]*, and values may not contain newlines.

  5. Container shell. Runs one command with /bin/sh -c in a chosen container through the Engine API and shows its output. The Hub stops waiting after 15 minutes, or when the browser request is cancelled. A process that keeps running inside the container is not killed.
  6. Restart app (enabled apps). A full down + up of the project, so override and env changes take effect. It waits for the result and, if it fails, shows compose's output like a failed enable.

Custom override¶

Typical uses: pin a different image tag, add environment variables, resource limits, extra bind mounts or named volumes, extra (literal) host ports, a healthcheck. Save override validates and stores it; it applies on the next restart ("restart to apply"), or when a disabled app is enabled. Saving an empty (or comment-only) override deletes the file. Every save, removal and refusal goes to the audit log as app.compose_override with the signed-in user, the size and a SHA-256 prefix, never the content (it may hold env values). The file is mode 0600.

The Hub refuses anything that would bypass Portcullis' routing or isolation. group-gate keys every policy and group by the subdomains the Hub reads from the template's Traefik labels, and the Hub's override sets each router's TLS options and middlewares, so the custom override may not change them:

  • Top level: only services, volumes, networks. Must be a mapping; no YAML tags (compose's !reset / !override could strip the template's labels or networks).
  • Services: only services the template defines, and only these keys: image, command, entrypoint, environment, labels, volumes, ports, expose, restart, healthcheck, user, working_dir, hostname, domainname, mem_limit, mem_reservation, memswap_limit, mem_swappiness, cpus, cpu_shares, cpuset, pids_limit, shm_size, ulimits, logging, tmpfs, extra_hosts, dns, dns_search, dns_opt, stop_grace_period, stop_signal, init, read_only, cap_drop, tty, stdin_open, pull_policy, platform, depends_on (on the template's services), oom_score_adj. Everything else is refused, in particular privileged, cap_add, devices, security_opt, network_mode, networks, pid, ipc, uts, userns_mode, cgroup, cgroup_parent, sysctls, volumes_from, extends, env_file, build, links, external_links, container_name, profiles, deploy, configs, secrets, group_add, runtime.
  • Labels: no traefik.* (routers, rules, middlewares, TLS options, entrypoints, services) and no com.docker.compose.* (the Hub finds the app's containers by them).

  • Volumes: named volumes, ./templates/<app>/…, or bind mounts of absolute host paths under the bind roots; everything else is refused, including /home, /var, /opt and /etc/localtime. The bind roots are HUB_OVERRIDE_BIND_ROOTS (colon-separated absolute paths, e.g. /srv:/mnt/media), default /srv:/mnt:/media. The Hub refuses to start if a root is /, is or contains a system path (/etc, /var/lib, /run, /usr, /tmp, …), contains the Docker socket or state, or overlaps the core checkout. Sources are cleaned (//, /./); .. segments, sockets (*.sock) and / itself are refused, as are shared/slave bind propagation and volume types other than bind, volume, tmpfs.

    Warning

    The Hub can't resolve symlinks on the host: a symlink under a bind root pointing elsewhere (e.g. /srv/x -> /) would be followed by the Docker daemon. What lives under the bind roots is the operator's responsibility; keep them to data directories.

  • Ports: literal host ports only (no variables); they count in the port checks against other enabled apps and against the app's own Settings ports.

  • Top-level volumes: only labels per volume (no driver, driver_opts, external or name: they could point at host paths or another app's data).
  • Top-level networks: only networks the template declares and doesn't mark external or name (so never portcullis-proxy), with labels, driver_opts, enable_ipv6, ipam.
  • No variables anywhere. Compose interpolates ${VAR} / $VAR in keys and values after the Hub's checks, so a label key ${T}raefik.enable would become traefik.enable. Every key and value with an unescaped $ is refused; write $$ for a literal dollar sign (compose turns it into $).

Because of these rules, the routes, subdomains, published snapshot and exposure drift the Hub computes from the template stay exact with a custom override in place. The override is checked again before every compose up: if a template update dropped a service it names (or it no longer passes), enable, restart and drift actions fail with HTTP 409 ("the custom compose override (Expert) is not valid for this template any more") before compose runs — edit or clear it.

Warning

A custom override can still break the app (a wrong image, a bad mount). It can't change how Portcullis routes and guards it.

Public exceptions¶

Some apps have share links meant for people without a Portcullis account (Nextcloud public shares, Grafana shared dashboards, Immich shared links). If the template declares them, the Settings tab shows a Public exceptions block (bordered in amber):

  • the template's description and every declared path with its description and kind: per share ({token} path), supporting, always opened (static assets) or all shares only;
  • a red warning: requests to these paths skip Portcullis entirely (no forward-auth, no group-gate, no hardware key); only the app's own checks (share token, share password, expiry) apply;
  • what is refused or stripped: core's public guard answers 403 to requests carrying Authorization, Proxy-Authorization or the app's login headers, cookies or query parameters (an app user signed in with "remember me" opens shares in a private window), and the Hub strips identity headers;
  • if the app's policy requires a client certificate at the TLS handshake (protected@file), an amber warning that all of the app's routers use authaware@file while a public path is open. For native-OIDC apps it adds that mTLS is then only enforced at login (Keycloak acr); for forward-auth / header-auth apps that group-gate still checks the client certificate on every gated request; and it lists routers without group-gate, which lose the handshake check. See Auth policies → Public exceptions.

Controls:

Control Meaning
Allow public exceptions On/off (an explicit admin choice)
Use the template default Forget the choice; the template's enabled_by_default applies, also after it changes on a template sync
Only listed shares / All shares Mode, if the template has {token} paths. Only listed: just the shares below. All: every share of the app
Listed shares Each listed token with Remove; a text box takes share URLs or bare tokens, one per line

The Hub extracts the token from a pasted URL (the {token} segment of the first matching path, e.g. https://cloud.example.org/s/AbC123/download → AbC123), checks it against the template's token_pattern and the alphabet [A-Za-z0-9._~-], rejects anything else (the save fails with the reason), and removes duplicates. At most 200 shares per app (each adds two matchers per {token} path to one Traefik rule). The status line shows what is open (with {token}, never the tokens) and on which subdomains, or "No public router is generated" — the case in mode listed with no share, which also keeps the handshake tier.

The list is admin-managed: ordinary app users can't publish a share to the internet themselves; they create the share in the app as usual (with its own password and expiry) and ask a Hub admin to list it. Remove the token (or turn the exception off) to close it again; the app's own share settings keep applying either way.

Saving regenerates the override and restarts the app. Any public choice (toggle, token list) also pins the mode it was made under, so a later template change can't widen it. Fail closed:

  • a stored mode the template no longer supports (e.g. listed after the template dropped its {token} paths) opens nothing and shows "public exception disabled … confirm a mode" in the block and as drift;
  • listed tokens the template's token_pattern no longer accepts are not routed and are shown as invalid (saving removes them).

The router is generated from the manifest, not shipped in compose.yml: only the Hub knows whether the exception is on, which shares are listed and which TLS tier the host gets, and a template can't open paths by itself.

Settings tab (global)¶

  • Default access policy. Applies to every app without its own policy. Until an admin saves one, the default is a YubiKey by either method, any of [mtls, webauthn]: a client certificate or a passkey. Apps without their own policy get authaware@file, and Keycloak steps up to at least LoA 2 (hwk). A certificate sign-in (mtls) satisfies it too. You can still choose a public default explicitly. That choice is stored and honoured, and differs from "never set". The default may name both factors; each app enforces what it can of it (an mtls app always requires the certificate, apps with their own sign-in get none). password is refused. Changing it re-applies it to every enabled app that inherits it, and restarts only the apps whose Traefik TLS tier actually changed. Saving an unchanged default does nothing.

User administration moved to the Users & Groups tab.

Users & Groups tab¶

Day-to-day user, group and field administration. LLDAP has no single sign-on, so its own web UI isn't published: directory.<domain> redirects to people.<domain>, and the LLDAP UI is reachable only from the server for recovery (portcullis lldap-ui). The Hub uses its own LLDAP service account, portcullis-hub, which core creates and mounts as files (see Integration Contracts §9). If core doesn't provide it, the tab says user management is disabled and everything else keeps working.

The tab has four sections: People, Groups, Org chart and Setup (admins only).

Access levels¶

  • Admins (hub.<domain>, members of lldap_admin) see and can change everything.
  • Everyone else (people.<domain>, any signed-in user) can view all people, groups, fields and the org chart, with three delegated permissions (granted per group by admins):
    • edit details: edit custom field values of non-protected accounts (single edits and CSV import)
    • invite: create new accounts with no groups (invite links only)
    • remove: delete accounts

Administrators signed in on people.<domain> get the same admin operations there as on hub.<domain>: core lets any signed-in user reach people.<domain>, and the Hub's own lldap_admin check (re-checked on every change) is the gate for admin operations on that listener.

Delegates cannot target themselves, administrators, the protected accounts (admin, portcullis-hub), or members of any permission group. Delegates cannot touch manual groups, exceptions or expiries; they can fill in fields that make people match rule-based groups. See Delegated permissions.

People¶

The People table shows every LLDAP user, with the custom field columns, groups (⚡ marks membership via a rule), Keycloak status (passkey count, required actions; admins only) and a search box. Clicking a row opens a dialog with details, groups (how membership was granted, expiries, exceptions), keys (admins only) and actions.

Invite (admins and delegates with the invite permission): creates a new user. Username (lowercase letters, digits, ., _, -; at least 2 characters), email, display name and groups (admins only). The user gets a one-time invite link (shown once, expires in 72 h): they register their passkey and are signed in, no password. A delegate's new account has no groups; filling in fields can make it match rule-based groups. Administrators get no invite links; the Hub shows ./portcullis invite <user> (server only). Under Advanced, admins can use a password fallback instead (generated or typed; 12 to 256 characters).

Import CSV (admins and delegates with any permission): see CSV import.

Per-person actions (in the dialog)¶

Action Who What it does
Edit details Admins, delegates with edit_details Change email, display name and custom field values (admin-only fields need an admin)
Send new invite Admins, delegates with invite (own keyless accounts only) New one-time link; earlier unused links stop working. Not offered for administrators
Require passkey Admins Adds the passkey registration action for the next sign-in
Clear pending Admins Removes pending required actions
Reset passkeys Admins Deletes all passkeys, signs the user out, then creates a new invite (or shows ./portcullis invite <user> for an administrator). Type the username to confirm
Password… Admins Fallback: set or generate a password; signs the user out
Remove Admins, delegates with remove Deletes the user from LLDAP and Keycloak. Type the username to confirm

Remove deletes the user from LLDAP first (saved as a tombstone to prevent re-creation of names still in exceptions/expiries), then deletes the Keycloak copy. The audit entry records what happened to the copy: keycloak_copy=removed, none (never imported) or FAILED. Delegates can remove only non-protected, non-administrator accounts not in any permission group. If the Keycloak removal fails, the copy is listed under Stale Keycloak records (admins only), where it can be removed by id. (Keycloak sometimes answers HTTP 500 after it has removed a federated user's copy; the Hub then looks the user up again and treats "not found" as removed.) The result also warns when other people's person fields (e.g. manager) or a rule's reports to still name the deleted user — update those.

Keycloak status (admins only)¶

For each LLDAP user except portcullis-hub:

  • not signed in yet: Keycloak has no copy. LDAP users are imported at first sign-in or when the Hub needs them (not an error)
  • passkey count, or no passkey
  • pending required actions
  • Keycloak status unavailable with the reason (per-user failure; only that row is affected)

The Hub reads each user's status separately, at most 8 calls at a time, 15 seconds total. A per-user failure marks only that user. If Keycloak itself is unreachable (sign-in, user list or federation list fails), a banner says "Keycloak status unavailable" and users/groups still load. Past 15 seconds, a banner says some statuses are missing.

Client certificates aren't shown; see enroll.<domain>.

Stale Keycloak records (admins only)¶

Users Keycloak has (federation link = LDAP provider) but LLDAP no longer has (deleted outside the Hub, e.g. in portcullis lldap-ui). The Hub lists the username, Keycloak id and reason.

Remove deletes only the Keycloak copy (type the username to confirm). The federation is read-only, so LLDAP isn't touched. Logged as keycloak.remove_stale with the id. Refused for admin, portcullis-hub, any username LLDAP has, and Keycloak users not linked to the LDAP federation.

Groups¶

Lists every LLDAP group with its member count, rule status (manual or rule-based), exceptions, expiries and the apps that use it. Clicking a group expands its details: members (with how they got in: manual, rule, or exception), the rule editor (for rule-based groups), exceptions and expiries, and the apps.

Create (admins): enter a group name ([A-Za-z0-9][A-Za-z0-9_.-]{0,127}, not starting with lldap_; case-insensitively unique). New groups are manual and start clean: if the Hub still has a rule, exceptions, expiries or a permission grant for that name (a group deleted in LLDAP's own UI), they are removed first and a warning lists them.

Delete (admins): type the name to confirm. Built-in groups (lldap_admin, lldap_password_manager, core-subdomain groups) can't be deleted. The group is deleted in LLDAP first (if that fails, nothing changes); then its rule, exceptions, expiries and any delegated permission granted to it are removed, so a group created later with the same name inherits nothing. Its former members are signed out of Keycloak.

Add / Remove member (admins): for manual groups only. Adding someone to an administrator group asks for confirmation. Removing yourself from lldap_admin is refused, and the last human member of lldap_admin stays. Removing a member also drops their expiry in that group (a later re-add starts without one) and signs them out of Keycloak; if the sign-out fails, the removal stands and a warning says so.

Set expiry (admins): for manual groups only. Pick a date/time (browser local time, converted to UTC); the membership is removed automatically when it expires. Clear it with No end. Refused for lldap_admin and for rule-based groups (use an exception instead).

Missing groups lists the access_group / admin_group (e.g. users_<app>, admin_<app>) of enabled apps that don't exist in LLDAP yet — until they do, nobody can use the app (or administer it). Each has a one-click Create. Templates not enabled add nothing here.

Rule-based groups¶

Admins can turn a group rule-based: membership is computed from custom fields. The rule is edited two ways that stay in sync:

  1. Blocks (default): point-and-click all/any blocks, nestable, with conditions is, is not, is one of (list fields), is empty, and for person fields reports to (directly or indirectly).
  2. Text rule: a typed expression with autocomplete (field names, list values) and inline errors. A toggle switches between them; a parse error refuses the toggle.

A preview shows who matches (count and names, live-updated). The Hub evaluates rules at least every 60 seconds, and on every detail change, rule change, exception change and import that affects membership.

Convert a manual group to rule-based (admins): opens a review. Current members who don't match are pre-ticked to stay as "added" exceptions (reason: "member before the rule (set by X on date)"); untick whoever should leave. Nothing changes until confirmed. The review compares itself with a fresh preview inside the Hub's lock and refuses with 409 if they differ (someone was added/removed in between) — convert again.

Exceptions (admins, rule-based groups only): add someone although the rule doesn't match them (they stay even if the rule changes), or keep out someone although the rule matches (the evaluator skips them). Each exception needs a written reason (≤ 500 characters, shown to everyone) and may have an expiry (date/time; they're removed automatically). The reason is required; without it the save fails.

Expiries on exceptions: an expired exception is kept (still denying for "kept out", doing nothing for "added" once the person left) until the person's membership changes (removed, re-added by an admin, another exception, rule add) or an admin deletes the exception.

Protected groups¶

Rules of administrator groups (see Administrators), permission groups (the groups holding a delegated permission) and app admin groups (any group used as an app's admin_group or in path_groups) may only reference admin-only fields. A field used by such a rule cannot lose its admin-only flag (409 until the rule is changed or the group stops being protected).

A protected group's rule also must not match a person with no details (e.g. office is empty or not office = "HQ"): every new account starts empty, so such a rule would hand the group to whoever creates accounts (409).

Delegate-created accounts (created_by, see Delegated permissions) are never added to a protected group by the evaluator, even if they match its rule; the evaluator reports them each run. They join once an admin acts on the account (sets a password, sends an invite, removes passkeys or requires a passkey), which clears created_by.

Built-in groups (lldap_admin, lldap_password_manager, core-subdomain groups) and permission groups cannot be rule-based.

The evaluator¶

  • Runs at least every 60 seconds, and immediately on detail/rule/exception/import changes.
  • Computes membership of every rule-based group (skips admin/built-in groups).
  • The Hub owns rule-group membership. A manual change made in LLDAP to a rule-based group (e.g. in portcullis lldap-ui) is reverted at the next evaluation and audited as such.
  • Handles cycles in the manager field (the reports to condition stops at the first repeat).
  • Removes expired memberships (manual and exceptions) from LLDAP after their expiry time. Expired entries are kept in the policy file's expiring array (plus a 10-minute grace period) so enforcement is strict even while the Hub is down. When group-gate withholds an expired membership for a request, it also withholds Authorization and X-Forwarded-Access-Token.
  • On every removal, the Hub revokes the user's Keycloak sessions, so OIDC apps lose access at their next token refresh (oauth2-proxy cookie refresh is 1 minute, so removals take effect within ~1 minute). The same happens for an admin's Remove member, a group Delete (all former members) and a password change; deleting a user deletes their Keycloak copy. Keycloak's LDAP federation caches no users, so group and field changes are read from LLDAP at that refresh.
  • An "added" exception with an end date is not published as expiring while the person is a member and matches the rule anyway (they stay by rule after the end); manual expiries and the 10-minute grace entries are always published.

Org chart¶

A tree of everyone's manager (the person field named manager, or the first person field if there is none). Shows cycles as a banner. If there is no person field, a message says so (admins: add one under Setup).

Everyone can see everyone's details and the org chart.

Setup (admins only)¶

Define custom fields and assign delegated permissions.

Custom fields¶

Fields describe people: department, office, cost center, manager, etc. Three kinds:

Kind Meaning
text Free-form text (one or multiple values per person)
list One of the values you maintain (e.g. "Milan", "Berlin", "Remote"). Multi-valued allowed
person A reference to another user (e.g. manager). Single-valued only

Per field:

  • Label (shown in the UI, e.g. "Department")
  • Share with apps (default on): the field becomes an OIDC claim (attr_<field>) for native-OIDC apps and an X-Forwarded-Attr-<Header-Name> header for forward-auth/header-auth apps. Attribute values are percent-encoded (% → %25, , → %2C), joined with ,, limited to 1 KB per value (before encoding; longer values are dropped and logged). Apps must percent-decode each value after splitting on ,. See Integration Contracts §4.1, §5.
  • Admin-only (off by default): only admins may edit it, and only admin-only fields may be used in rules of protected groups (administrator, permission and app-admin groups).

Create: name (^[a-z][a-z0-9]*(_[a-z0-9]+)*$, at most 31 characters: lowercase letters and digits, starting with a letter, _ only between two of them — not at the end, not doubled; so its header name is always valid and unique; unique, and not one of LLDAP's built-in attributes: mail, uid, display_name, first_name, last_name, avatar, creation_date, uuid, user_id), label, kind, multi-valued (not for person fields), share with apps, admin-only. For list fields, add the allowed values.

Edit: change the label, values (list fields; can't remove a value in use), share-with-apps and admin-only flags. Can't change kind or multi. Can't turn off admin-only while a protected group's rule uses the field (409).

Delete: type the name to confirm. Refused (409) if a rule uses it, with the groups listed.

Fields are stored in LLDAP as custom user attributes (non-user-editable, so users can't change their own department in portcullis lldap-ui). Rules, exceptions, expiries, field metadata LLDAP can't hold, and permission assignments live in the Hub's state ($HUB_DATA_DIR/directory.yaml, atomic, mode 0600; a corrupt file refuses to start).

Delegated permissions¶

Three permissions, each granted to a group (manual or rule-based; that group may itself use rules over non-admin-only fields):

Permission What it grants
edit details Update email, display name and custom field values (single edits and CSV import). Admin-only fields need an admin
invite Create new accounts via invite link (no groups, no Keycloak credentials). Filling in fields can make them match rule-based groups. A delegate-created account shows "via rule, account created by X" for its rule memberships
remove Delete accounts

Delegates never target themselves, administrators (lldap_admin etc.), the protected accounts (admin, portcullis-hub) or members of any permission group. They can't create a tombstoned name or one still in exceptions/expiries. A delegate's Send new invite works only for accounts the delegate created that still have zero Keycloak credentials (Keycloak missing or unavailable → refused); admins should re-invite such accounts themselves if they gave them only a client certificate. An admin's password / invite / passkey action clears the account's created_by, so delegates can't re-invite it.

Permission changes (including refusals) are audited (directory.permission). Built-in, admin and rule groups using non-admin-only fields are refused (409). Set a permission to (none) to revoke it.

CSV import¶

Import CSV (admins and delegates with any of edit_details, invite, remove) uploads a CSV file (, or ; separator, optional BOM, CRLF; at most 5 MB, 10,000 rows, 64 columns) and opens an editable review table. Nothing changes until Apply. The review:

  • One row per person: new, changed, missing (in LLDAP but not in the file; unticked by default) or unchanged (hidden by default, with a Show unchanged toggle)
  • Changed cells show current → file; click ↺ to keep the current value
  • Edit any cell
  • Problems (red): block Apply until fixed. Example: a manager who isn't a known user, with a picker to fix it. Unknown columns are reported but don't block
  • Effect on rule-based groups: +n / −n per group, ignoring missing rows
  • Download CSV: the edited table with a formula-neutralising leading ' for cells that start with =, +, -, @ or `, or with tab/CR. That ' is stripped on re-import, so a downloaded review imports back unchanged
  • Re-review (JSON of the edited {header, rows}): refreshes the Effect with current rules

Columns:

  • username (required), display_name, email and every custom field name. Unknown columns are listed but don't block.
  • Missing people (LLDAP users not in the file) show up as unticked rows. Tick to remove (needs remove permission).
  • Can't clear email or display name (the cell must have a value).

Apply: processes rows one by one (no rollback). Each row is re-checked with the caller's permissions (delegates: can't create into groups, can't touch protected/admin/permission-group accounts, can't create a tombstone). New people get invite links (admins and delegates with invite). The result shows per-row ok/error and invite links.

The Hub writes shared fields (those with share-with-apps on) into user-attributes.json, which group-gate reads to populate X-Forwarded-Attr-* headers (§4.1). On every field or membership change, the Hub also syncs the Keycloak LDAP attribute mappers and protocol mappers on the portcullis-attributes client scope (each shared field → portcullis-attr-<field> LDAP mapper → attr_<field> protocol mapper).

Administrators¶

Members of these groups are administrators:

  • lldap_admin and lldap_password_manager
  • the groups of the core subdomains (auth, traefik, hub, directory, enroll, people, metrics) in group-gate/group-gate-map.conf (Hub: HUB_GATE_MAP_FILE)
  • any group listed in INVITE_PROTECTED_GROUPS

This is the same set core's invite API uses. An invite hands the account to whoever holds the link, so core refuses invites for administrators, and the Hub doesn't offer them. Invite or recover an administrator on the server with ./portcullis invite <user>. If core refuses an invite for a group the Hub doesn't know about, the Hub shows "administrators are recovered from the server: ./portcullis invite <user>".

Guardrails¶

  • portcullis-hub (the Hub's own account) and admin (the bootstrap LLDAP admin) are untouchable: no edits, passwords, invites, passkey actions, group changes or deletion. An invite for admin would hand over the root account, so recover it on the server: ./portcullis invite admin.
  • Administrators get no invites from the Hub. Resetting another administrator's passkeys or setting their password lets you take over their account: you must type their username to confirm, and the audit entry is flagged (target_is_lldap_admin=true).
  • admin and portcullis-hub can't be created. lldap_* group names are reserved. Built-in groups can't be deleted or made rule-based.
  • You can't delete yourself or remove yourself from lldap_admin.
  • The last human member of lldap_admin (every member except portcullis-hub) can't be deleted or removed from it.
  • Email addresses are unique (case-insensitive).
  • Every change goes through the same proxy-secret and CSRF checks as the rest of the Hub and needs a signed-in user (X-Forwarded-User).

Audit log¶

Every change, including refused and failed attempts, is appended to audit.jsonl in $HUB_DATA_DIR (mode 0600). Each entry records the time, actor (X-Forwarded-User), action, target, optional detail, result (ok / refused / error) and optional error. The log never contains passwords, tokens or invite links. The tab (admins only on hub.<domain>) shows the last 100 entries. On people.<domain>, GET /api/directory/audit is 403.

How passwords are set¶

LLDAP stores passwords with OPAQUE. Its HTTP password endpoints need the client half of that protocol, so the Hub sets passwords over LDAP instead (the standard Password Modify operation, RFC 3062). LLDAP then does the OPAQUE step itself. This is the same mechanism ldappasswd uses. The password crosses the portcullis network in clear text, like Keycloak's and enroll's LDAP binds; core may switch to LDAPS with LLDAP_LDAP_URL=ldaps://….

Drift detection¶

The Hub keeps the desired state (enabled apps) in state.yaml and regularly compares it with the compose projects Docker actually runs:

  • every HUB_RECONCILE_INTERVAL (default 1m, at least 5s)
  • on Docker events

Reconcile reports drift and never fixes it by itself. A yellow State drift box at the top of the catalog lists each mismatch with a message, the running/total container count, and buttons for the allowed actions:

Kind (kind in the API) Meaning Actions
enabled_not_running Enabled, but no container of the project runs (stopped, or none) Start (start: compose up), Disable (disable)
running_not_enabled Containers of portcullis-<id> run, but the app is not enabled (the message adds "its public-exception router bypasses forward-auth" if they carry one) Stop & remove (stop: compose down). Enable (adopt: mark it enabled and compose up) when a template with that ID exists
stopped_not_enabled Stopped containers left behind by an app that is not enabled Stop & remove (stop)
template_missing Enabled, but no valid template provides it any more (source removed, template deleted or now invalid) Disable (disable)
public_access_mismatch An exposure label of a running container (any router's tls.options, any label of the public router or its strip middleware, and for apps with their own login every router's middlewares, e.g. after switching the Sign-in mode without a restart) differs from what the Hub renders now — a widened rule, a missing guard or other middleware, a stale or missing public router (e.g. after a failed restart or a template change) — or a stored public choice can't be applied ("confirm a mode") Apply settings (apply: regenerate the override and compose up), Disable (disable); none for "confirm a mode" (fix it in Settings)

Destructive actions ask for confirmation. Re-check runs a reconcile immediately. Apps that are in the middle of an operation are skipped.

The same is available over the API, which also needs the proxy secret:

GET  /api/drift            latest report: {checked_at, error?, items: [{id, kind, message, running, total, template_exists, actions}]}
POST /api/drift            re-check now, returns the new report
POST /api/drift/resolve    {"id": "<app>", "action": "start|disable|stop|adopt|apply"}

If Docker is unreachable, the report carries error and the UI shows "Docker unreachable".

Fail-closed behaviour¶

Drift must never open access. That is why state.yaml keeps a snapshot (published) of each enabled app's last published config: subdomains, access group, admin paths, policy override, whether it ran with its own login only (then no group is published: its routers have no group-gate) and the public paths it opened (with {token}). The containers keep the public router they were started with, so the snapshot keeps showing it in the policy file's public_paths.

  • Template missing, snapshot present. If an enabled app's template stops loading, the Hub keeps publishing the snapshot to group-gate, so the app stays protected exactly as before. The drift message says "template missing — still enforced from last known config", plus "configured for the app's own login only" for such apps.
  • No snapshot. If an enabled app has no snapshot, or a portcullis-<id> project runs without being enabled, the Hub reads the Host() rules from the running containers' labels. It publishes the reserved group __portcullis_deny__ for those subdomains. group-gate then denies every request to them ("The configuration of … is unavailable"), until you disable or adopt the app. Never create an LLDAP group with that name.
  • Corrupt state.yaml. If the file can't be parsed (or is empty), the Hub refuses to start rather than overwrite it with empty state.

Template rules enforced by the Hub¶

Templates must load cleanly, or the Hub skips them and logs why:

  • The manifest must satisfy the templates repo's schema.
  • The directory name must match ^[a-z0-9][a-z0-9_-]{0,63}$.
  • Setting, port and env keys must be valid .env keys.
  • Port bind values must be IP addresses.
  • auth.method must be one of the schema's methods; auth.native_login only with method: custom, sso: false and supported: true.

Strict Traefik rule parsing. group-gate keys every policy, group and path rule by subdomain. A host the Hub doesn't see would get no policy and no group, which fails open. So the Hub parses each traefik.http.routers.<name>.rule label in compose.yml and rejects the template if:

  • a Host() argument is anything but a literal `<label>.${PORTCULLIS_DOMAIN}` (a default such as ${PORTCULLIS_DOMAIN:-portcullis.local} is allowed). That rules out other domains, bare domains, and variables in the label part (${SUB}.${PORTCULLIS_DOMAIN})
  • the rule uses HostRegexp, HostHeader, HostSNI or HostSNIRegexp
  • some way the rule can match is not restricted by Host(): a top-level || branch without Host(), a negation, or a path-only rule
  • a router has no rule, or a traefik.enable=true service has no HTTP router. Traefik would then apply its default rule
  • it declares a TCP router, which would bypass forward-auth
  • it routes a core subdomain (auth, traefik, hub, directory, enroll, metrics)

Keycloak clients¶

For templates with keycloak_clients, the Hub creates confidential OIDC clients in the portcullis realm. Each client gets:

  • the secret from the app's generated env
  • the manifest's redirect URIs, with {{DOMAIN}} replaced
  • default.acr.values set from the app's policy
  • the default client scopes openid, profile, email, plus acr (puts acr/amr in tokens for step-up) and groups (claim groups with plain group names, so apps can map users_<app> / admin_<app>)
  • with email_verified_claim: false in the manifest, email-unverified instead of email (claim email, no email_verified; created by ./portcullis keycloak configure). The Hub attaches it first, then removes email from the client's default and optional scopes, on create and on every reconcile; without the realm scope it logs an error and leaves email in place (contract §8)

Ownership. Each client the Hub creates is tagged with the attribute portcullis.hub.template=<template-id>. When the client already exists, the Hub updates its secret, redirect URIs, ACR and scopes only if:

  • the client is tagged and the tag names this template, or
  • the client is untagged and the Hub can prove it belongs to the template. That means it has at least one redirect URI, and every redirect URI and web origin is a plain http(s) URL without wildcards whose host is one of the template's own <sub>.<domain> hosts.

Anything else fails closed. The existing client is left untouched and the enable is refused with HTTP 409 (client "<id>" … belongs to someone else). The app is not started, because it would be wired to a secret and redirect URIs it doesn't own. Resolve the clash in Keycloak, e.g. by deleting the foreign client or choosing another client_id. Other registration errors, such as Keycloak being unreachable, are logged as warnings, and the app still starts.

Core and built-in clients are reserved and never touched: portcullis-forward-auth, admin-cli, account, account-console, broker, realm-management and security-admin-console.

Per-app isolation¶

  • Separate compose project. Each app runs as portcullis-<app-id>, with its own containers and default network.
  • Networks. Frontends join the external portcullis-proxy network (shared with Traefik) and the app's default network. Internal services join only default. Apps can't reach each other or the core services directly.
  • Template files. Before every compose up, the Hub copies the app's template directory to <core>/templates/<app-id>/. Compose resolves relative paths against the core checkout on the host (--project-directory = PROJECT_HOST_DIR), which is what makes bind mounts like ./templates/immich/setup.sh work.
  • Separate .env. The Hub writes a per-app .env with the app's settings, generated secrets (generate: random → 32 hex characters), and the core variables its compose file references. It takes those core variables from /project/.env, which is not the core .env: it is the generated subset secrets/hub/core.env (see Security & Hardening). Files are written atomically with mode 0600.

Template sources¶

Each source is a git repository with one directory per app (manifest.yaml + compose.yml).

  • Default source. On first start, the Hub clones porelli/portcullis-templates (DEFAULT_TEMPLATES_URL) as the source named portcullis. It cannot be removed.
  • Sync. Runs git pull --ff-only on every source and reports which failed to fast-forward. The Hub never edits the clones (the Expert tab's custom override lives in the Hub's data directory), so syncs fast-forward.
  • Community sources. Add more repositories in the Template Sources tab.
    • Source names use lowercase letters, digits, - and _.
    • URLs must be https://…, http://…, ssh://… or user@host:path.
    • Removing a source first stops every enabled app from it.

Templates from all sources are merged into one catalog. Remember that a template runs with what is effectively host-root power (see below). Only add sources you trust.

Security model¶

  • Authentication. The Hub has no login of its own. Traefik enforces forward-auth and the lldap_admin group (hub=lldap_admin in core's group-gate-map.conf) before a request reaches it.
  • Proxy secret. Every request except GET /healthz must carry X-Portcullis-Proxy-Secret equal to HUB_PROXY_SECRET. The comparison is constant-time, the secret must be at least 32 characters, and the Hub won't start without it. Traefik's hub-proxy-secret@docker middleware adds the header after forward-auth, so a container that reaches the Hub directly on the portcullis network can't impersonate an admin by sending X-Forwarded-User. See Security & Hardening.
  • Portal list. Next to the policy file the Hub writes portal-apps.json: enabled apps with name, icon, URLs and required group, for core's landing portal (Integration Contracts §10).
  • CSRF. Every state-changing request (POST/PUT/DELETE) must be same-origin (checked through Sec-Fetch-Site/Origin) and carry Content-Type: application/json. The forward-auth cookie is shared across all *.<domain> subdomains, so without this a page on any other app would count as "same-site".
  • Docker access. The Hub has no Docker socket. It uses DOCKER_HOST=tcp://socket-proxy-hub:2375 both for the docker compose CLI (only up/down) and for its own Engine API calls (status, logs, exec, events). The socket proxy denies swarm, plugins, builds, secrets, configs and system prune. The Hub can still start containers with any configuration, so treat it as host-root-equivalent.
  • Runtime user. The image runs as uid/gid 10001 with a read-only root filesystem. It writes only /data (the hub_data volume), /project/templates (chowned to 10001 by ./portcullis up) and tmpfs. secrets/ and backups/ of the core checkout are masked with empty tmpfs mounts.
  • Outbound calls. The Hub calls the Keycloak admin API, LLDAP (GraphQL, plus LDAP only to set passwords) and core's invite API, with Go's HTTP client: 20 s timeouts, TLS verification, no shelling out to curl. Credentials never appear in process arguments or env vars: the LLDAP service account and the invite secret are read-only files mounted by core. The signed-in user shown in the header is X-Forwarded-User as-is, i.e. the LLDAP username. The Hub never looks it up in LDAP.
  • LLDAP admin rights. The Hub's service account is in lldap_admin, so the Hub can grant lldap_admin. That adds nothing to what it can already do: through its socket proxy it is host-root-equivalent. Every change is attributed to the signed-in admin and audited.
  • Timeouts. compose up 15 min, compose down 5 min, shell 15 min, git 5 min.

  • Policy file. The Hub writes group-gate-policy.json (version 3) atomically to hub_data. It is keyed by subdomain only:

    • policies for apps with an override (apps that inherit publish nothing; group-gate uses default)
    • groups for enabled apps with group_access: true
    • path_groups from auth.admin_paths
    • core subdomains are never published

    The format is defined in Integration Contracts §4.

Image tags and verification¶

X.Y.Z, X.Y, X, sha-<short> A release tag vX.Y.Z is pushed

There is no latest tag. On core main, HUB_IMAGE defaults to ghcr.io/porelli/portcullis-hub:edge. A core release pins a released Hub tag by digest, and release.yml enforces that. If you override it, pin a release by tag and digest in .env, then run ./portcullis up. ./portcullis version shows which image is configured and which one runs.

cosign verify ghcr.io/porelli/portcullis-hub:<tag> \
  --certificate-identity-regexp '^https://github.com/porelli/portcullis-hub/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

Common tasks¶

Changing an app's subdomain or middlewares¶

Routing comes from the template only. Change the Host() rule or the router middlewares in the template, in a template source you control (fork the template into your own source repository if needed), keep the rule in the strict form and keep the forward-auth pair (portcullis-auth@docker,portcullis-groups@docker, in this order) and security-headers@file. Sync, then restart the app. The new subdomain must not be used by another enabled app; the Hub re-publishes the group and policy under it. The Expert tab's custom override refuses traefik.* labels.

Backing up app data¶

App data lives in Docker volumes named portcullis_<name> (templates declare explicit names). ./portcullis backup covers the core volumes only. Back up app volumes with your usual tooling, e.g.:

docker run --rm -v portcullis_jellyfin_config:/data -v "$PWD":/backup \
  alpine tar czf /backup/jellyfin-config.tar.gz -C /data .
