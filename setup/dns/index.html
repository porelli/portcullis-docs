DNS Configuration¶

Portcullis uses wildcard DNS to route all subdomains to a single server. This page covers how to set up DNS records and configure your DNS provider for automatic certificate issuance.

Prerequisites¶

  • A domain you control (e.g., example.com)
  • DNS hosted on a supported provider (Cloudflare, Porkbun, Route53, DigitalOcean, Hetzner, or any lego provider)
  • A server with a public IP running Portcullis

Step 1: Configure DNS¶

Option A: Wildcard DNS Record (Recommended)¶

Create a single wildcard A record pointing all subdomains to your server:

*.portcullis.example.com  A  203.0.113.10

This means auth.portcullis.example.com, hub.portcullis.example.com, grafana.portcullis.example.com, and every other service subdomain all resolve to your server without creating individual records.

You also need a record for the bare subdomain:

portcullis.example.com    A  203.0.113.10

Cloudflare proxy

If using Cloudflare, disable the orange cloud (proxy) for the wildcard record. Cloudflare's proxy interferes with mTLS client certificate verification.

Option B: Individual DNS Records¶

If you prefer explicit records, create one for each service:

portcullis.example.com            A  203.0.113.10
auth.portcullis.example.com       A  203.0.113.10
directory.portcullis.example.com  A  203.0.113.10
enroll.portcullis.example.com     A  203.0.113.10
hub.portcullis.example.com        A  203.0.113.10
people.portcullis.example.com     A  203.0.113.10
traefik.portcullis.example.com    A  203.0.113.10
metrics.portcullis.example.com    A  203.0.113.10   (monitoring profile only)

You will need to add a record each time you enable a new app.

Step 2: Create a DNS Provider API Token¶

Portcullis needs a DNS API token to solve ACME DNS-01 challenges for wildcard certificate issuance. Only *.portcullis.example.com appears in Certificate Transparency logs -- individual subdomain names are never leaked.

Cloudflare¶

  1. Go to API Tokens
  2. Click "Create Token" and use the "Edit zone DNS" template
  3. Permissions: Zone > DNS > Edit
  4. Set in .env:
DNS_PROVIDER=cloudflare
CLOUDFLARE_API_TOKEN=your-token

Porkbun¶

  1. Go to API Access
  2. Enable API access for your domain
  3. Create an API key and secret key
  4. Set in .env:
DNS_PROVIDER=porkbun
PORKBUN_API_KEY=pk1_...
PORKBUN_SECRET_API_KEY=sk1_...

AWS Route 53¶

DNS_PROVIDER=route53
AWS_ACCESS_KEY_ID=your-key
AWS_SECRET_ACCESS_KEY=your-secret
AWS_HOSTED_ZONE_ID=Z1234567890

DigitalOcean¶

DNS_PROVIDER=digitalocean
DO_AUTH_TOKEN=your-token

Hetzner¶

DNS_PROVIDER=hetzner
HETZNER_API_KEY=your-key

Other Providers¶

Traefik supports 80+ DNS providers via lego. Set DNS_PROVIDER=<lego-provider-name> and its required environment variables in .env.

Traefik is configured entirely through environment variables in the core docker-compose.yml (there is no traefik.yml). If your provider's environment variables are not already listed there, add them to the traefik service's environment section in a docker-compose.override.yml (it is part of every backup).

Step 3: Configure Portcullis¶

First-time setup¶

./portcullis init asks for your domain and DNS provider (credentials are read from the environment or a hidden prompt), writes them to .env and, for the providers it knows, creates the records from Step 1 for you:

./portcullis init

Creating or checking the records later¶

./portcullis dns setup           # create/update A (and AAAA) for <domain> and *.<domain>
./portcullis dns setup --check   # only compare what resolves (via 1.1.1.1) with the public IP

dns setup supports cloudflare, porkbun, digitalocean, hetzner and route53 (needs the aws CLI). For other providers it prints the records to create by hand. See the CLI Reference.

Changing the provider or credentials¶

Edit .env:

ACME_EMAIL=admin@example.com
DNS_PROVIDER=porkbun
PORKBUN_API_KEY=pk1_...
PORKBUN_SECRET_API_KEY=sk1_...

Then restart the stack so Traefik picks up the new environment:

./portcullis up

Traefik requests and renews the wildcard certificate automatically.

Changing the domain

PORTCULLIS_DOMAIN is baked into the Keycloak realm (redirect URIs, hostname), LLDAP_BASE_DN, the server certificate and every enabled app's config. Pick it before init; changing it later means a new install.

Step 4: Verify¶

Check that the certificate was issued:

# Check Traefik logs for ACME
docker compose logs traefik | grep -i acme

# Test with curl
curl -v https://auth.portcullis.example.com 2>&1 | grep "subject:"

You should see a Let's Encrypt certificate for *.portcullis.example.com.

How ACME DNS-01 Works¶

Unlike HTTP-01 challenges (which require port 80 access for each hostname), DNS-01 proves domain ownership by creating a TXT record in your DNS zone:

  1. Traefik requests a wildcard certificate for *.portcullis.example.com
  2. Let's Encrypt responds with a challenge token
  3. Traefik uses your DNS provider's API to create a _acme-challenge.portcullis.example.com TXT record
  4. Let's Encrypt verifies the TXT record exists
  5. The wildcard certificate is issued, covering all subdomains

This is why Portcullis needs your DNS provider API token -- it creates and cleans up the challenge TXT record automatically.

One domain per installation¶

A Portcullis installation serves exactly one base domain, PORTCULLIS_DOMAIN, and every app lives at <subdomain>.${PORTCULLIS_DOMAIN}. This is enforced, not just a default:

  • group-gate denies every request whose host is not exactly <label>.${PORTCULLIS_DOMAIN}, because it looks policies and groups up by that label
  • the Hub rejects templates whose routers use any other domain (Integration Contracts §4)
  • Traefik requests one wildcard certificate (${PORTCULLIS_DOMAIN} and *.${PORTCULLIS_DOMAIN})
  • oauth2-proxy's cookie and redirect whitelist cover .${PORTCULLIS_DOMAIN} only
  • Keycloak's hostname is auth.${PORTCULLIS_DOMAIN}

To serve a second domain, run a second installation. Supporting several domains in one installation would need all of the following:

  • group-gate keyed by full host, or by a domain list
  • the Hub's host validation and policy file keyed the same way
  • a certificate and DNS records per domain
  • oauth2-proxy cookies per domain: a session cookie can't span unrelated domains, so users would sign in once per domain
  • Keycloak redirect URIs for each domain

Local Development (No Public Domain)¶

For local development without a real domain or ACME:

  1. Run ./portcullis init --domain portcullis.local --dns-provider none. init already issues a self-signed *.portcullis.local server certificate from the internal PKI (certs/server.crt; ./portcullis pki setup --with-server-cert recreates it)
  2. Add entries to /etc/hosts:
127.0.0.1  portcullis.local auth.portcullis.local directory.portcullis.local enroll.portcullis.local hub.portcullis.local people.portcullis.local traefik.portcullis.local
  1. Import certs/root-ca.crt into your browser or OS trust store to avoid certificate warnings

Note

mTLS with client certificates works the same way locally. The only difference is the server certificate is self-signed instead of from Let's Encrypt.
