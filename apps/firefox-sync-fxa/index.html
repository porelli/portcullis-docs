🦊 Firefox Sync + own accounts¶

Firefox Sync with its own self-hosted Mozilla accounts, for the access group by verified email; nothing depends on Mozilla

Category: productivity
Tags: firefox, sync, bookmarks, browser, mozilla, accounts
Website: https://mozilla-services.github.io/syncstorage-rs/
Source: https://github.com/porelli/firefox-sync
Minimum resources: 4 GiB RAM, 18 GiB disk

About¶

Firefox Sync keeps bookmarks, passwords, history, open tabs and add-ons in step across a person's Firefox browsers, on desktop and phone. This template runs the whole stack on your server, Mozilla's account service included, so nothing depends on Mozilla and the data is stored only on your server.

Sync data is end-to-end encrypted with keys from each person's account: the server stores it but can't read it.

Portcullis decides who may have an account: the instance's access group, matched by each person's verified Portcullis email. The accounts of people who leave the group are disabled and signed out, and the account pages and the admin UI sit behind Portcullis sign-in.

Needs about 4 GB of RAM and 18 GB of disk (upstream's sizes), plus about 5 GB for Mozilla's accounts image.

Auth Notes

Firefox Sync with its own, self-hosted Mozilla accounts: Firefox signs in and syncs on this server, and nothing depends on Mozilla. Only members of the instance's access group with a verified Portcullis email can have an account.

Hosts (the default instance's names; each instance has its own, shown on its page):

  • Behind Portcullis sign-in: firefox-sync-fxa-accounts.<domain>, the account pages (sign-up, sign-in, settings), for the access group; and firefox-sync-fxa-admin.<domain>, the admin UI, for the admin group only.
  • Open to the internet, because Firefox calls them in the background without cookies: firefox-sync-fxa-api.<domain> (the accounts API), firefox-sync-fxa-profile.<domain> (profiles and avatars), firefox-sync-fxa.<domain> (Sync storage, each request signed with the account's own keys) and firefox-sync-fxa-pairing.<domain> (an encrypted relay for pairing a phone by QR code).
  • On the accounts host, the start page /, /.well-known/fxa-client-configuration, /.well-known/change-password and /metrics-flow stay open too: Firefox reads them before anyone has signed in.
  • Every open host is rate-limited; creating an account and getting a Sync token have a stricter limit.
  • The Sync, API and accounts hostnames are fixed once the instance exists. The Sync data depends on them: the Sync server keeps every account as <account id>@<API host> on its node, the Sync host, and every Firefox keeps the accounts and API addresses it was set up with. A new name would leave every Sync store behind and every Firefox calling the old addresses. The profile, pairing and admin hostnames can change. A change of Portcullis's main domain doesn't move them either: the instance is listed as error until the old domain is added as an extra domain. A restore into a new instance id keeps the archive's fixed hostnames, so the old instance must be gone first; the other three get the new id's own. Other fixed hostnames mean a new instance, with new accounts.

Who may have an account: the members of the instance's access group with a verified Portcullis email. Each person verifies their email with a code sent to it (this needs the server's mail provider): verify it on your People page. An admin can also mark someone else's email verified there. A member without a verified email can't sign up: no verified email, no account. fxa-access-sync writes the verified emails to the sign-up list at every start and whenever the group changes.

  • Someone who leaves the group, or whose email changes or stops being verified, is taken off the list. Their account is disabled and signed out everywhere, and within about 5 seconds the admin UI revokes the access tokens their Firefox holds. Firefox can keep syncing for up to about 20 minutes after that: nothing can take back a Sync token it already has (it lasts up to 15 minutes), and the Sync server trusts an access token it already checked for up to 5 more minutes.
  • The admin UI does that revoking, for every disable and sign-out. It always runs with the instance and restarts on its own. If it's down (stopped by hand, or failing), a held access token stays valid until the admin UI starts again, or up to 60 minutes, and Firefox can sync for up to about 20 minutes after that.
  • Every run also disables and signs out any enabled account whose current primary email isn't on the list. An account's email can't be changed here, but if one was changed some other way, this catches it.
  • That sweep has a brake: if it would disable more accounts than the run expects (the people who left, plus 2), it disables none. The run is then reported as failed with the numbers only, and isn't tried with a higher limit. Check the accounts in the admin UI.
  • When they come back, their account is enabled again, even one an admin disabled before the person left.
  • An account an admin disables stays disabled while its owner stays in the group: routine runs never enable it.
  • If the list delivered by Portcullis can't be read, nothing changes and the run is reported as failed.

Admin UI (porelli/firefox-sync's admin UI), for the instance's admin group only. Others get 403 at the gateway, members of the access group included. After the Portcullis sign-in, the admin UI signs in by OpenID Connect with Portcullis's Keycloak (client firefox-sync-fxa-admin, redirect URI exactly https://<admin host>/auth/callback), which admits only the admin group (admin_firefox-sync-fxa, from the groups claim, never by email). There is no password sign-in.

  • Portcullis decides who may sign up and sync, not the admin UI (access managed elsewhere): the sign-up policy, its allowlist, invitations, the account cap and Sync's max users are shown read-only, and their forms answer 403. The account cap is the instance setting Maximum accounts.
  • Kept for incidents: monitoring, the event log, account pages and notes, per-account sign-out, disable and enable, deleting an account, and the Sync data tools. Enable refuses an account whose current primary email isn't on the list ("not on the access list managed elsewhere"). Deleting an account leaves the list alone, so a member whose account was deleted can sign up again.
  • Confirm email and Confirm this sign-in are refused (403 at the gateway). Only the code sent to the address proves an account's email, so an admin can't vouch for one. Someone who signed up with a member's address, or signed in with a stolen password, would get in without that mailbox.
  • Its Connect a device page shows the Firefox setup below with this server's values.

Mail: the sign-up and sign-in codes go out through the server's mail provider (Settings, Mail) by default, at most 10 messages a minute and 60 an hour; or through another SMTP server (the instance's Mail settings). Without either, the accounts server doesn't start, and fxa-mail-check says why.

  • STARTTLS on 587 is required, never opportunistic: a server that doesn't offer it gets no mail and never sees the password. Use TLS from the start on 465. TLS on 587 or STARTTLS on 465 stops the start.
  • The mail server's certificate is checked against the server's CA bundle (certs/ca-bundle.crt: the host's system CAs, Portcullis's own CA, and Let's Encrypt staging while ACME_STAGING=true). For a mail server with a self-signed certificate, add its CA to the host's system trust store, run ./portcullis config apply --bundle-only, then restart the instance.

What's refused, and why:

  • Adding a second email or changing an account's email is refused at the gateway (403). An account's email is its Portcullis email, and access follows that email.
  • Confirming an email or a sign-in in the admin UI is refused at the gateway (403): only the code sent to the address counts.
  • Passwordless sign-in and Google or Apple sign-in are refused (403). Every account is created through the sign-up gate, which checks the list.
  • Email addresses that aren't plain ASCII are refused by the accounts database. Emails are compared byte for byte, so a look-alike address (an accent or a full-width letter) never matches a member's. An existing account with such an email is disabled and signed out at every start.

Backups: the fxa-keys volume holds the accounts' signing keys; a Hub instance backup copies it with the databases. Losing it signs everyone out: every Firefox must sign in again.

Firefox setup (the accounts URL is the instance's accounts host, https://firefox-sync-fxa-accounts.<domain> for the default one). Sign out of Firefox first, if it's signed in.

  • Desktop: in about:config, set identity.fxaccounts.autoconfig.uri to the accounts URL. Restart Firefox, then sign in and turn on Sync.
  • Android: Settings, About Firefox, tap the logo 5 times. Back in Settings, open Sync Debug and set Custom Mozilla account server to the accounts URL. Leave Custom Sync server empty. Restart Firefox when it asks, then sign in.
  • iOS: in Settings, tap the version number 5 times. Open Advanced Sync Settings, turn on Use Custom FxA Content Server and set Custom Account Content Server URI to the accounts URL. Then sign in.
  • A phone can also pair from a signed-in desktop (Settings, Sync, Connect another device) once its accounts URL is set.

What runs: Mozilla's accounts (auth, content and profile servers, v1.350.0) on MySQL with Redis, the pairing channel server, syncstorage-rs 0.25.2 on PostgreSQL, and porelli/firefox-sync's admin UI and sign-up gate, as built by porelli/firefox-sync (links.source; upstream https://github.com/mozilla/fxa and https://github.com/mozilla-services/syncstorage-rs). fxa-gate, an nginx that answers only Traefik, is in front of every host; no other service of the instance is reachable from other apps.

AI support¶

No AI support: Signs people in with its own Mozilla accounts, not Portcullis identities, and Sync data is end-to-end encrypted; no MCP server known (surveyed 2026-11-26).

Settings¶

Options an admin sets in the Hub's settings panel (person-entered ones: each person, on My apps). Scope and Applies are explained in the Manifest Reference.

Setting Type Scope Applies Description
Send mail through enum instance restart Where the sign-up and sign-in codes go out. The server's mail provider needs one wired (Settings, Mail); without a working mail server the accounts server doesn't start. Choices: provider, external. Default: provider.
SMTP server string instance restart Another SMTP server only. Its host name.
SMTP port int instance restart Another SMTP server only. 587 for STARTTLS, 465 for TLS; the accounts server doesn't start with TLS on 587 or STARTTLS on 465. Default: 587.
SMTP security enum instance restart Another SMTP server only. STARTTLS on 587 or TLS from the start on 465. Choices: starttls, tls. Default: starttls.
SMTP user string instance restart Another SMTP server only. Empty when it takes mail without signing in.
SMTP password secret instance restart Another SMTP server only. The password of the SMTP user; it can't contain ', \ or a line break.
Sender address string instance restart Another SMTP server only. The address the mail comes from, shown as Firefox accounts.
Maximum accounts int instance restart At most this many accounts; sign-ups are refused once they exist. Empty: no limit, the access group decides.
Account email verified_email instance restart Each member's verified Portcullis email: the email they may create their Firefox account with. Members without a verified email can't.
