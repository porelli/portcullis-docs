# 🔐 Vaultwarden

> Lightweight Bitwarden-compatible password manager

**Category:** security  
**Tags:** `passwords`, `bitwarden`, `vault`, `secrets`

## Authentication

| Property | Value |
|----------|-------|
| **Method** | `native-oidc` |
| **SSO** | :white_check_mark: Yes |
| **Group Access** | :x: |
| **Group Admin** | :x: |
| **Access Group** | `users_vaultwarden` |
| **Admin Group** | `admin_vaultwarden` |
| **Admin Paths** | `/admin` (require `admin_vaultwarden` in addition to access) |
| **Subdomain** | `passwords` |

!!! info "Auth Notes"
    Native SSO via OpenID Connect. Users still need a master password for vault encryption. The admin panel (/admin) sits behind forward-auth + group-gate and, through auth.admin_paths, requires membership of admin_vaultwarden; Vaultwarden's ADMIN_TOKEN (VAULTWARDEN_ADMIN_TOKEN) is still required on top, keep it secret. No group-based access restriction on the vault itself. Identity: SSO accounts are keyed on the OIDC subject (issuer + sub); SSO_SIGNUPS_MATCH_EMAIL is false, so an SSO login is never attached to an existing account by email (LLDAP emails are user-editable). Already linked SSO users sign in normally. New SSO signups are refused while Keycloak sends email_verified=false (Vaultwarden only accepts true or an absent claim, see SSO_ALLOW_UNKNOWN_EMAIL_VERIFICATION); until the Vaultwarden client stops receiving that claim, invite new users from /admin and have them register with a master password. A user whose email collides with an existing account is refused, never merged.

| Router | Host | Paths | TLS tier | Forward-auth + group-gate |
|--------|------|-------|----------|---------------------------|
| `vaultwarden` | `passwords.<domain>` | all | `authaware@file` | :x: |
| `vaultwarden-admin` | `passwords.<domain>` | `/admin` | `authaware@file` | :white_check_mark: |
