!!! info "Auth Notes"
    Native OIDC through Wiki.js' generic OpenID Connect strategy (key "portcullis"), configured by the wiki-setup sidecar at every start over the internal network (GraphQL, with its own API key kept in the wiki-setup-data volume). One Portcullis login: the login page offers only "Portcullis". No password login: the sidecar disables the local strategy (and its self-registration), so the internet-facing GraphQL login and register mutations refuse local accounts. Traefik only routes the wiki while its healthcheck passes, which needs the Portcullis strategy enabled and the local one disabled: the setup wizard of a fresh install, and a re-enabled local login, get 404 from Traefik. Identity: Wiki.js keys accounts on the OIDC subject (the Keycloak id of the LLDAP user, never the email; Wiki.js has no username-claim option). It requires an email claim and keeps emails unique per strategy, so an account's email is only profile data, but: it would link a login to a user an admin pre-created for this strategy with the same email (never pre-create users for the Portcullis strategy), and a user who sets their LLDAP email to another user's address makes the later login of whichever of them is second fail (denial of service, no takeover; fix the email in LLDAP). Rights come only from groups: new accounts get no group, and at each login Wiki.js sets the user's membership of the Wiki.js groups users_wiki (editors, created once; adjust its rights in Wiki.js) and admin_wiki (manage:system, re-applied every start) from the groups claim. A realm user outside access_group can't sign in (Keycloak denies it, see below) and would have no rights anyway. The Guests group has no permissions (re-applied before every boot by wiki-init and by the sidecar), so nothing is readable anonymously. Removing a user from the groups takes effect at their next login (Wiki.js sessions last up to 14 days). Break-glass, on the server only: docker compose -p portcullis-<instance> exec wiki-db psql -U wiki -d wiki -c "UPDATE authentication SET \"isEnabled\" = true WHERE key = 'local'", restart the wiki container, open Wiki.js directly on its container address (e.g. an SSH tunnel to <container ip>:3000; Traefik serves 404 meanwhile) and sign in as admin@wiki.invalid with WIKI_ADMIN_PASSWORD; the next start of the app (Hub) disables the local login again. Existing installs: local accounts can no longer sign in; reset or remove them in Administration > Users (as an SSO admin) since their passwords stay valid if the local login is ever re-enabled. If the sidecar has neither its API key nor the local admin admin@wiki.invalid / WIKI_ADMIN_PASSWORD (installs whose first admin had another email), it can't configure anything and the wiki stays unrouted: create that local admin through the break-glass steps and restart. Hostname: wiki-init writes the site URL from the instance's hostname before Wiki.js boots, so a hostname change only needs a restart. Sign-in is restricted to access_group in Keycloak (keycloak_access_role, contract §8 Access role): only access_group members can sign in, so a member of admin_group who is not also in access_group is denied — put the wiki's admins in both groups.

## Environment Variables

Per-app variables in the generated `.env`; `random` ones are generated by the Hub on first enable:

| Variable | Description | Generation |
|----------|-------------|------------|
| `WIKI_DB_PASSWORD` | Wiki.js database password | `random` |
| `WIKI_ADMIN_PASSWORD` | Password of the local Wiki.js admin admin@wiki.invalid (its login is off; break-glass only) | `random` |
| `WIKI_OIDC_SECRET` | Wiki.js OIDC client secret | `random` |
