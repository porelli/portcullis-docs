|----------|-------|

| **SSO** | :white_check_mark: Yes |
| **Group Access** | :white_check_mark: |
| **Group Admin** | :white_check_mark: |
| **Access Group** | `users_homeassistant` |
| **Admin Group** | `admin_homeassistant` |
| **Subdomain** | `home` |

!!! info "Auth Notes"
    Home Assistant 2026.10 has no OpenID Connect of its own; sign-in goes through the OpenID Connect custom integration auth_oidc (christiaangoossens/hass-oidc-auth, the integration HACS lists, here pinned to release 1.2.1 and installed by the homeassistant-init one-shot from the release asset after its SHA-256 matched; a mismatch stops the start. Its Python requirements ship in the Home Assistant image). It is the only auth provider: configuration.yaml (shipped read-only) sets auth_providers: [] so Home Assistant's own username/password login doesn't exist, and homeassistant-init marks onboarding done before the first start, so the onboarding wizard (which creates a password owner) never opens. The app is routed only while /auth/providers lists auth_oidc alone and onboarding is closed. Who can sign in: auth_oidc admits users in users_homeassistant (roles.user) and also users in admin_homeassistant alone (roles.admin implies access upstream), so the Hub's Keycloak access role (keycloak_access_role) restricts the client to users_homeassistant as well: in production only that group gets a token at all. admin_homeassistant members become Home Assistant administrators. Upstream sets roles only when the account is created (first login): change an existing user's administrator flag in Settings > People. Accounts are keyed on the OIDC issuer + sub, the display name is the LLDAP username (preferred_username), and SSO logins are never linked to existing accounts (automatic_user_linking off). No one is the instance owner; administrators can do everything an owner can except owner-only operations. Break-glass: there is no local login; an operator temporarily mounts a modified configuration.yaml (with a local provider) over the template's through the Hub's custom override. What works: the web UI and its websocket API (straight to Home Assistant, no forward-auth on the host), long-lived access tokens created by a signed-in user, and the Companion apps: upstream signs mobile apps in with a device code shown in the app and confirmed in a browser (Chrome/Safari or another computer) where the user signs in to Portcullis. That device-code step is phishable: a member can be tricked into entering a code an outsider's app shows, which signs that app in as the member (enter only codes from your own device). Limits: removing a user from the groups blocks new sign-ins only. Home Assistant refresh tokens stay valid until unused for 90 days and long-lived access tokens are effectively permanent (upstream has no session management or back-channel logout yet): deactivate the user in Home Assistant (Settings > People) to revoke them. Networking: the container is on Docker bridge networks only (never host networking, which would publish port 8123 past the gateway), so mDNS/SSDP/DHCP discovery, Bluetooth and USB radios are not available; use IP-based integrations (or MQTT / a network radio bridge). The HTTP server settings (Traefik as the only trusted proxy) are rewritten by homeassistant-init at every start; changes made in the UI don't persist. That is also why several instances can run side by side (instances: multi). Upgrades: read the Home Assistant and hass-oidc-auth release notes; bump auth_oidc (version and SHA-256 in init.py) together with Home Assistant when upstream requires it.
